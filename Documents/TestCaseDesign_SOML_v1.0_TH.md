# 1. บทนำ

## 1.1 จุดประสงค์

เอกสารนี้ระบุรายละเอียดของกรณีทดสอบ TC-01 ถึง TC-14 ในระดับที่ผู้อื่นนำไปดำเนินการซ้ำแล้วได้ผลเหมือนเดิม โดยระบุเงื่อนไขก่อนทดสอบ ข้อมูลนำเข้าที่ใช้จริง ขั้นตอนเรียงเป็นข้อ ผลลัพธ์ที่คาดหวัง และเกณฑ์ตัดสินผ่านหรือไม่ผ่าน

บทที่ 3 หัวข้อ 3.9 ของปริญญานิพนธ์ระบุกรณีทดสอบไว้เป็นสรุปบรรทัดเดียวต่อหนึ่งกรณี ซึ่งเพียงพอสำหรับการนำเสนอในรูปเล่ม แต่ไม่พอให้ผู้ทดสอบคนอื่นดำเนินการตามได้ เอกสารฉบับนี้จึงขยายรายละเอียดส่วนที่ขาด และเพิ่มการจับคู่กับชุดทดสอบอัตโนมัติที่เขียนไว้จริงในซอร์สโค้ด เพื่อให้ตรวจสอบได้ว่ากรณีทดสอบแต่ละข้อถูกดำเนินการด้วยอะไรและได้ผลจากไหน

## 1.2 ขอบเขต

เอกสารครอบคลุมการทดสอบสองชั้นที่ทำงานร่วมกัน

**ชั้นที่หนึ่ง กรณีทดสอบเชิงความต้องการ TC-01 ถึง TC-14** เป็นกรณีที่ออกแบบจากเกณฑ์การยอมรับ AC-01 ถึง AC-15 แต่ละกรณีตอบคำถามว่าความต้องการข้อหนึ่งถูกทำให้เป็นจริงแล้วหรือยัง

**ชั้นที่สอง กรณีทดสอบอัตโนมัติ 92 กรณี** ที่เขียนด้วย Jest และสคริปต์ทดสอบระดับระบบ เป็นตัวดำเนินการจริงที่ให้ผลลัพธ์แก่ชั้นที่หนึ่ง กรณีทดสอบอัตโนมัติหลายกรณีอาจรวมกันเป็นหลักฐานของกรณีทดสอบเชิงความต้องการเพียงข้อเดียว

เอกสารไม่ครอบคลุมการทดสอบความปลอดภัยเชิงลึกอย่างการเจาะระบบ การทดสอบภาระงานที่เกินเกณฑ์ที่กำหนด และการทดสอบบนอุปกรณ์จริงทุกรุ่น ซึ่งอยู่นอกขอบเขตของโครงงาน

# 3. เทคนิคที่ใช้ออกแบบกรณีทดสอบ

การแปลงเกณฑ์การยอมรับหนึ่งข้อให้เป็นกรณีทดสอบใช้เทคนิคห้าอย่าง เลือกตามลักษณะของสิ่งที่ต้องพิสูจน์

| เทคนิค | ใช้เมื่อ | กรณีทดสอบที่ใช้ |
|---|---|:---:|
| เส้นทางปกติ (Happy Path) | ต้องยืนยันว่าเมื่อทุกอย่างเป็นไปตามที่คาดไว้ ระบบให้ผลลัพธ์ถูกต้อง | TC-02, TC-03, TC-09, TC-12 |
| ค่าขอบเขต (Boundary Value) | เงื่อนไขมีจุดตัด และข้อผิดพลาดมักเกิดที่รอยต่อมากกว่ากลางช่วง | TC-08, TC-10, TC-11 |
| การแบ่งกลุ่มสมมูล (Equivalence Partitioning) | ข้อมูลนำเข้าแบ่งเป็นกลุ่มที่ระบบควรปฏิบัติเหมือนกันภายในกลุ่ม | TC-01 |
| การเปลี่ยนสถานะ (State Transition) | สิ่งที่ทดสอบมีสถานะและมีเส้นทางเปลี่ยนสถานะที่อนุญาตกับที่ห้าม | TC-06, TC-08 |
| สภาวะแข่งขัน (Concurrency) | ข้อผิดพลาดปรากฏเฉพาะเมื่อมีการกระทำต่อข้อมูลชุดเดียวกันพร้อมกัน | TC-04, TC-06, TC-14 |

**เหตุผลที่ต้องมีเทคนิคสภาวะแข่งขัน** ปัญหาการนำบิลเก่ามารับสินค้าซ้ำที่ระบุไว้ในหลักฐาน EV-06 เป็นปัญหาที่การทดสอบเส้นทางปกติพิสูจน์ไม่ได้เลย เพราะการยืนยันจ่ายสินค้าทีละครั้งจะให้ผลถูกต้องเสมอ แม้ระบบจะไม่มีกลไกป้องกันการจ่ายซ้ำอยู่เลยก็ตาม กรณีทดสอบ TC-06 จึงต้องยิงคำขอพร้อมกันหลายคำขอ และต้องทำซ้ำหลายรอบ เพราะสภาวะแข่งขันเป็นปัญหาที่เกิดแบบไม่แน่นอน ทดสอบรอบเดียวแล้วผ่านไม่ได้แปลว่าไม่มีปัญหา

**เหตุผลที่ต้องมีเทคนิคการเปลี่ยนสถานะ** คำสั่งซื้อมีสี่สถานะและมีเส้นทางที่อนุญาตกับที่ห้ามชัดเจนตามแผนภาพสถานะในรูปที่ 3.13 การทดสอบต้องครอบคลุมทั้งเส้นทางที่อนุญาต เช่น รอจ่ายสินค้าไปเป็นกำลังจัดของ และเส้นทางที่ห้าม เช่น การข้ามไปเป็นส่งมอบสำเร็จโดยไม่ผ่านธุรกรรมตัดสต็อก

4. ทดสอบเส้นทางความล้มเหลวแยก โดยชี้ที่อยู่ของบริการพิมพ์ไปยังพอร์ตที่ไม่มีบริการใดฟังอยู่ แล้วยืนยันรับชำระอีกครั้ง
5. ตรวจว่าคำสั่งซื้อยังถูกบันทึกและเข้าคิวตามปกติ

**ผลลัพธ์ที่คาดหวัง** ใบเสร็จพิมพ์เสร็จภายใน 5 วินาทีนับจากเวลาที่กดยืนยัน และเมื่อเครื่องพิมพ์ไม่พร้อม คำสั่งซื้อยังถูกบันทึกและเข้าคิวคลังตามปกติพร้อมแสดงคำเตือน

**เกณฑ์ตัดสิน** ค่าสูงสุดจากการวัดทั้ง 30 ครั้งไม่เกิน 5,000 มิลลิวินาที ไม่มีครั้งใดที่การพิมพ์ล้มเหลว และในเส้นทางความล้มเหลว คำสั่งซื้อตอบรหัส 201 พร้อมสถานะรอจ่ายสินค้า โดยผลการพิมพ์แจ้งว่าไม่สำเร็จ

**ข้อจำกัดที่ต้องระบุ** ตัวเลขที่วัดได้เป็นเวลาที่ระบบใช้ประกอบชุดคำสั่ง ESC/POS และส่งออกเท่านั้น ยังไม่รวมเวลาที่เครื่องพิมพ์ความร้อนใช้พิมพ์และตัดกระดาษจริง ซึ่งเป็นส่วนที่กินเวลามากที่สุด การทวนสอบ NFR-05 จึงยังไม่สมบูรณ์จนกว่าจะวัดซ้ำที่สถานประกอบการ ดูแบบฟอร์มในหัวข้อ 8.2

# 9. บันทึกข้อบกพร่องที่พบจากการทดสอบ

หัวข้อนี้บันทึกข้อบกพร่องที่ชุดทดสอบจับได้จริงระหว่างการพัฒนา เป็นหลักฐานว่าการออกแบบกรณีทดสอบทำหน้าที่ของมันจริง ไม่ใช่เพียงยืนยันสิ่งที่ทำงานอยู่แล้ว

## DEF-01 เลขที่คำสั่งซื้อชนกันเมื่อบันทึกพร้อมกัน

| หัวข้อ | รายละเอียด |
|---|---|
| พบโดย | TC-04 ส่วนที่ยิงคำขอพร้อมกัน |
| อาการ | ยิงคำขอสร้างคำสั่งซื้อพร้อมกัน 50 รายการ สำเร็จเพียง 24 รายการ ที่เหลือล้มเหลวด้วยข้อผิดพลาดเลขที่ซ้ำ |
| สาเหตุ | ทุกคำขออ่านเลขที่ล่าสุดของวันได้ค่าเดียวกัน แล้วแย่งกันบันทึก จนการลองใหม่ครบจำนวนที่กำหนด |
| การแก้ไข | ล็อกช่วงเลขที่ของวันไว้ตั้งแต่ขั้นตอนอ่าน คำขอที่เข้ามาพร้อมกันจึงได้เลขที่เรียงต่อกันทีละราย และเพิ่มการถอยหลังแบบสุ่มก่อนลองใหม่ |
| ผลหลังแก้ | ยิงพร้อมกัน 50 รายการสำเร็จครบ 50 รายการ ไม่มีข้อผิดพลาด |
| ข้อสังเกต | กรณีทดสอบตามที่บทที่ 3 กำหนดไว้เดิม คือสร้าง 100 รายการต่อเนื่องกัน ไม่สามารถเปิดเผยข้อบกพร่องนี้ได้เลย เพราะการสร้างทีละรายการไม่เกิดสภาวะแข่งขัน จึงต้องเพิ่มการทดสอบแบบยิงพร้อมกันเข้าไป |

# 10. ภาคผนวก

## 10.1 คำสั่งรันชุดทดสอบ

```sh
cd app

npm test                  # ทดสอบระดับหน่วยและระดับการทำงานร่วมกัน พร้อมรายงานความครอบคลุม
npm run test:unit         # เฉพาะระดับหน่วย ไม่ต้องใช้ฐานข้อมูล
npm run test:integration  # เฉพาะระดับการทำงานร่วมกัน
npm run test:system       # TC-05, TC-13, TC-14 และการตรวจ NFR-01 ต้องเปิดเซิร์ฟเวอร์ไว้ก่อน
npm run test:tc06         # TC-06 จำนวน 30 รอบ รอบละ 10 คำขอพร้อมกัน
npm run test:browsers     # เมทริกซ์เบราว์เซอร์สำหรับ NFR-07
npm run check:privacy     # ตรวจว่าภาพหลักฐานไม่มีหมายเลขพร้อมเพย์จริงฝังอยู่
```

ชุดทดสอบระดับการทำงานร่วมกันรีเซ็ตฐานข้อมูลทดสอบให้เองก่อนเริ่มทุกครั้ง จึงรันซ้ำได้โดยไม่ต้องเตรียมอะไรเพิ่ม ส่วนชุดทดสอบระดับระบบต้องเปิดเซิร์ฟเวอร์และบริการพิมพ์ไว้ก่อนด้วย `npm run serve`
