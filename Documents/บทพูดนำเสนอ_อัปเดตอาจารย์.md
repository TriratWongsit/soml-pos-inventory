# หน้า 2 · ขอบเขตของโครงงาน

**พูด**\
ขอบเขตมี 5 ข้อครับ อยู่ในหัวข้อ 1.3\
ข้อแรกเป็นเว็บที่ใช้ได้ทั้งคอมและมือถือ มีผู้ใช้ 3 บทบาท คือพนักงานขาย พนักงานคลัง แล้วก็ผู้จัดการ\
ข้อสองคือเข้าสู่ระบบ แยกสิทธิ์ตามบทบาท และจัดการสินค้า\
ข้อสามคือหน้าขาย มี QR พร้อมเพย์ พิมพ์ใบเสร็จ แล้วส่งใบสั่งเข้าคิวคลังทันที\
ข้อสี่คือคิวคลังแบบเรียลไทม์ กดยืนยันจ่ายแล้วตัดสต็อกทีเดียวจบ\
ข้อห้าคือแดชบอร์ด ประวัติการทำรายการ กับแจ้งเตือนในแอป\
ส่วนที่ไม่ทำ เช่น ระบบบัญชีเต็มรูปแบบ ตรวจยอดโอนกับธนาคารอัตโนมัติ แอปมือถือแบบ native กับแจ้งเตือนผ่าน LINE ครับ

**ถ้าอาจารย์ถาม** ทำไมไม่ตรวจยอดโอนอัตโนมัติ\
ต้องใช้ API ของธนาคาร ซึ่งร้านต้องไปสมัครกับธนาคารเอง และเกินเวลาของโครงงานครับ ตอนนี้พนักงานดูยอดเข้าในแอปธนาคารแล้วค่อยกดยืนยันในระบบ

**ดูในเล่ม** หัวข้อ 1.3 ขอบเขต และ 1.3 ส่วนนอกขอบเขต

# หน้า 3 · จากขอบเขตเป็น Requirement 18 ข้อ

**พูด**\
จากขอบเขต 5 ข้อ ผมได้ requirement ทั้งหมด 18 ข้อครับ เป็น FR 9 ข้อ กับ NFR 9 ข้อ\
หน้านี้โชว์ว่าแต่ละข้อมาจากขอบเขตข้อไหน เช่น ขอบเขตข้อ 1.3.4 คิวคลังกับตัดสต็อก ได้ FR-04 FR-05 FR-06 แล้วก็ NFR-02 เรื่องคิวต้องขึ้นภายใน 3 วินาที กับ NFR-04 เรื่องกดพร้อมกันแล้วต้องไม่พัง\
มี 2 ข้อที่ไม่ได้มาจากขอบเขตตรง ๆ ครับ คือ NFR-08 ที่มาจากสมมติฐานว่าใช้สถาปัตยกรรม 3 ชั้น กับ NFR-09 ที่ระบบต้องติดตั้งที่ร้านได้จริง

**ถ้าอาจารย์ถาม** ทำไมต้องมี NFR-09\
เพราะถ้าติดตั้งที่ร้านไม่ได้ ระบบก็ไม่ได้ใช้จริงครับ ตอนนี้ผู้จัดการร้านลงเองตามคู่มือ ใช้ประมาณ 5 นาที ผ่านแล้วครับ

**ดูในเล่ม** บทที่ 3 ตาราง FR และ NFR · หน้าสืบย้อน Traceability

# หน้า 4 · Requirement มาจาก Stakeholder ไหน

**พูด**\
Requirement ไม่ได้คิดเองครับ ผมไปดูการทำงานที่ร้าน แล้วคุยกับเจ้าของร้านกับพนักงาน สิ่งที่เจอผมจดเป็นหลักฐาน EV-01 ถึง EV-09\
Stakeholder มี 7 กลุ่มครับ เป็นคน 6 กลุ่ม คือพนักงานขาย พนักงานคลัง ผู้จัดการ ลูกค้า เจ้าของร้าน กับผู้จัดทำ แล้วก็ระบบอัตโนมัติอีก 1\
ยกตัวอย่างนะครับ\
พนักงานขายตอนนี้เขียนบิลกับคิดเงินเอง คือ EV-01 เลยได้ FR-03\
ลูกค้าต้องถือบิลเดินไปคลังแล้วยืนรอ คือ EV-04 เลยได้ FR-04 กับ NFR-02 ให้คลังเห็นใบสั่งทันที\
ผู้จัดการอยากรู้ว่าของใกล้หมดเมื่อไร อยากดูย้อนหลังว่าใครทำอะไร เลยได้ FR-07 FR-08 FR-09\
ส่วนผู้จัดทำ เป็นคนที่ต้องดูแลกับติดตั้งระบบต่อ เลยเป็นเจ้าของ NFR-08 เรื่องแยกชั้นให้แก้โค้ดง่าย กับ NFR-09 เรื่องติดตั้งที่ร้านได้

**ถ้าอาจารย์ถาม** ทำไมไม่นับอาจารย์ที่ปรึกษาเป็น stakeholder\
อาจารย์ตรวจโครงงานครับ แต่ไม่ได้ใช้ระบบ และไม่ได้อะไรจากระบบ ผมเลยนับเฉพาะคนที่ได้หรือเสียประโยชน์จากตัวระบบจริง ๆ

**ถ้าอาจารย์ถาม** แล้วทำไมผู้จัดทำนับ\
เพราะหลังส่งมอบ ผู้จัดทำต้องแก้โค้ดและลงเครื่องใหม่ให้ร้าน ถ้าโค้ดแยกชั้นไม่ดี หรือติดตั้งยาก คนที่ลำบากคือผู้จัดทำครับ

**ถ้าอาจารย์ถาม** เก็บความต้องการมายังไง\
ไปสังเกตการทำงานที่ร้าน กับสัมภาษณ์เจ้าของร้านและพนักงาน จดสิ่งที่เห็นเป็น EV ทีละข้อ แล้วค่อยแปลงเป็น requirement ครับ

**ดูในเล่ม** บทที่ 3 ตารางหลักฐาน EV · เอกสารผู้มีส่วนได้ส่วนเสีย หัวข้อ 1

# หน้า 5 · ประเภทของ Requirement

**พูด**\
สรุปตัวเลขครับ requirement 18 ข้อ มาจาก stakeholder 7 กลุ่มที่เพิ่งพูดไป\
แบ่งเป็นสองแบบครับ\
FR 9 ข้อ คือสิ่งที่ระบบต้องทำได้ เช่น เข้าสู่ระบบ สร้างคำสั่งซื้อ ตัดสต็อก แจ้งเตือน\
NFR 9 ข้อ คือระบบต้องดีแค่ไหน ผมแยกตามด้านคุณภาพครับ\
ด้านความเร็วมี 3 ข้อ คิวต้องขึ้นภายใน 3 วินาที ใบเสร็จออกภายใน 5 วินาที แล้วรับผู้ใช้พร้อมกัน 10 เซสชัน\
ด้านความปลอดภัยคือ NFR-01 ตรวจสิทธิ์ทุกคำขอ ด้านความน่าเชื่อถือคือ NFR-04 กดพร้อมกันแล้วสต็อกไม่เพี้ยน\
ที่เหลือคือ ใช้บนมือถือได้ ใช้ได้หลายเบราว์เซอร์ แยกชั้นให้แก้โค้ดง่าย กับติดตั้งที่ร้านได้ครับ

**ถ้าอาจารย์ถาม** FR กับ NFR ต่างกันยังไง\
FR บอกว่าระบบทำอะไรครับ เช่น ตัดสต็อกได้ ส่วน NFR บอกว่าทำได้ดีแค่ไหน เช่น ตัดแล้วคิวขึ้นภายใน 3 วินาที กดพร้อมกันแล้วไม่พัง NFR ทุกข้อผมใส่เกณฑ์ที่วัดได้ไว้ เลยทดสอบได้ว่าผ่านหรือไม่

**ดูในเล่ม** บทที่ 3 ตาราง FR และ NFR

# หน้า 8 · สถาปัตยกรรมระดับ C2

**พูด**\
ต่อไปเป็นการออกแบบครับ ระดับ C2 ผมแบ่งเป็น 3 ชั้น คือหน้าจอ ตรรกะ แล้วก็ข้อมูล แต่ติดตั้งจริงเป็น 4 ตัว\

# หน้า 12 · UC-01 เข้าสู่ระบบและควบคุมสิทธิ์

**พูด**\
UC-01 เป็นด่านแรกของทุกคนครับ พนักงานกรอกชื่อกับรหัสที่หน้า login ส่งไป POST /api/auth/login โมดูล Auth เทียบรหัสกับตาราง users\
ถ้าถูก ระบบให้บัตรผ่านหรือโทเคน ที่บอกว่าคนนี้เป็นบทบาทอะไร แล้วจดลงประวัติว่าใครเข้าระบบตอนไหน\
หลังจากนั้นทุกคำขอต้องผ่าน Auth Middleware ไม่มีบัตรตอบ 401 มีบัตรแต่ไม่ใช่หน้าที่ตัวเองตอบ 403\
ทดสอบด้วย TC-01 ลองไม่มีบัตร บัตรปลอม บัตรของบทบาทอื่น ถูกปฏิเสธครบทุกกรณี ผ่านครับ

**อธิบายเส้น**\
ก่อนเข้า use case แรก ขออธิบายวิธีอ่านภาพหน่อยครับ\
อ่านจากซ้ายไปขวา 5 ช่อง คือ use case หน้าจอ API โมดูลหลังบ้าน แล้วก็ตารางในฐานข้อมูล\
เส้นสีส้มคือทางที่ use case นี้วิ่งผ่านจริง เส้นที่ข้ามจากช่องหนึ่งไปอีกช่องคือเรียกต่อกัน\
เส้นโค้งที่ออกทางขวาของช่อง Backend แล้ววนกลับเข้าช่องเดิม คือโมดูลเรียกโมดูลด้วยกัน\

# หน้า 22 · UC-11 การแจ้งเตือนในแอป

**พูด**\

**อธิบายเส้น**\

จากหน้าจอ notifications มี 2 เส้น ไป /api/notifications (GET และ PATCH อ่านแล้ว) กับ WebSocket /ws (สำรองเป็น SSE) คือหน้าจอนี้ส่งคำขอไปหลังบ้านผ่าน API สองตัวนี้\
/api/notifications (GET และ PATCH อ่านแล้ว) วิ่งเข้าโมดูล Alert Engine\
เส้นโค้งทางขวาของช่อง Backend คือโมดูลเรียกกันเองครับ Alert Engine เรียก Queue Manager กับ Audit Log\
เส้นสุดท้ายไปช่องขวาสุด คือโมดูลไหนใช้ตารางไหนครับ Alert Engine ใช้ตาราง notifications กับ products · Audit Log ใช้ตาราง audit_logs
