# 1. Introduction

## 1.1 Purpose

เอกสารนี้กำหนดความต้องการซอฟต์แวร์ของระบบจัดการคำสั่งซื้อและตรวจสอบคลังสินค้า (อำพร OMS) สำหรับร้านวัสดุก่อสร้างอำพรคอนกรีต โดยเล่าผ่านกรณีการใช้งาน (Use Case) UC-01 ถึง UC-11 พร้อมลำดับเหตุการณ์หลัก ทางเลือก และข้อยกเว้น (Main / Alternate / Exception Flow) และเกณฑ์การยอมรับ (Acceptance Criteria) เพื่อให้ผู้พัฒนา ผู้ทดสอบ อาจารย์ที่ปรึกษา และเจ้าของร้านตรวจสอบขอบเขต พฤติกรรม กฎทางธุรกิจ แบบจำลอง และการสอบกลับ (Traceability) ร่วมกันได้จากเอกสารฉบับเดียว ความต้องการทุกข้อสืบกลับไปยังหลักฐานหน้างาน EV-01 ถึง EV-09 ในปริญญานิพนธ์บทที่ 3

เวอร์ชัน 2.0 นี้เป็น Review Candidate ยังไม่ใช่ Baseline เพราะความต้องการนอกเหนือหน้าที่บางข้อ (NFR-05 เวลาพิมพ์ใบเสร็จ NFR-06 ภาระงานพร้อมกัน และ NFR-09 การติดตั้งซ้ำ) ยังไม่ได้ทวนสอบกับเครื่องพิมพ์จริงและสภาพแวดล้อมจริงของร้าน รายการเหล่านี้ระบุไว้ใน Appendix C

## 1.4 Product Scope

ร้านวัสดุก่อสร้างอำพรคอนกรีตมีจุดชำระเงินหน้าร้านและจุดจ่ายสินค้าที่คลังอยู่คนละที่ และใช้บิลกระดาษเป็นตัวกลางระหว่างสองจุด ทำให้ยอดสินค้าคงเหลือในบันทึกไม่ตรงกับของจริง มีการนำบิลเก่ามารับสินค้าซ้ำ และคลังไม่ทราบล่วงหน้าว่ามีคำสั่งซื้อใดรออยู่ (EV-01 ถึง EV-09) ระบบอำพร OMS จึงต้องเป็นแหล่งข้อมูลหลักของคำสั่งซื้อและสต็อก ให้หน้าร้านกับคลังเห็นข้อมูลชุดเดียวกันทันที และให้ผู้จัดการติดตามภาพรวมได้โดยไม่ต้องเดินไปดู

| In Scope | Out of Scope / นอกขอบเขต |
|--------------------------------------------------|--------------------------------------------------|
| เว็บแอปพลิเคชันแบบ Responsive สำหรับสามบทบาท: พนักงานขาย พนักงานคลังสินค้า ผู้จัดการ | แอปพลิเคชันแบบ Mobile Native |

# 2. Overall Description

## 2.1 Product Perspective

อำพร OMS เป็นระบบใหม่ที่พัฒนาขึ้นแทนการใช้บิลกระดาษเป็นตัวกลางระหว่างจุดชำระเงินหน้าร้านกับจุดจ่ายสินค้าที่คลัง ระบบเป็นแหล่งข้อมูลหลัก (System of Record) ของคำสั่งซื้อ ยอดสินค้าคงเหลือ การเคลื่อนไหวสต็อก และประวัติการทำรายการ ตัวเลขที่แสดงทุกจุดต้องมาจากข้อมูลชุดนี้ ไม่มีสมุดหรือบิลคู่ขนาน ผู้ใช้สามบทบาทเข้าถึงระบบผ่านเบราว์เซอร์ และระบบติดต่อกับองค์ประกอบภายนอกสองรายการ คือเครื่องพิมพ์ใบเสร็จความร้อนที่หน้าร้าน (ระบบส่งคำสั่งพิมพ์ออกไป) และแอปพลิเคชันธนาคารของลูกค้า (ระบบแสดงรหัส QR ให้สแกน แต่ไม่ได้รับข้อมูลใดกลับ)

ลูกค้าไม่ใช่ผู้ใช้ระบบ เพราะไม่มีบัญชีและไม่กระทำการใดกับระบบโดยตรง การยืนยันว่าเงินเข้าแล้วเป็นการกระทำของพนักงานขายหลังตรวจจากแอปพลิเคชันธนาคารด้วยตนเอง ข้อเท็จจริงนี้กำหนดพฤติกรรมของระบบทั้งหมด และเป็นเหตุผลที่ระบบไม่มีสถานะ "รอชำระเงิน" (ดู 2.5 CON-03)

## 2.3 User Classes and Characteristics

| Actor / User Class | เป้าหมายและลักษณะ | Authority Boundary |
|----------------|------------------------------------------|------------------------------------------|
| พนักงานขาย (Sales) | อยู่ประจำจุดชำระเงินหน้าร้าน ต้องบันทึกการขายและออกใบเสร็จได้ในหน้าจอเดียวขณะลูกค้ายืนรอ ค้นหาสินค้า สร้างคำสั่งซื้อ แสดงรหัส QR ยืนยันรับชำระเงิน | ยืนยันจ่ายสินค้า แก้ไขข้อมูลสินค้า ดูแดชบอร์ด ประวัติ และการแจ้งเตือนไม่ได้ |
| พนักงานคลังสินค้า (Warehouse) | เดินอยู่ในคลัง ใช้แท็บเล็ตหรือมือถือ ต้องรู้ว่ามีคำสั่งซื้อรออยู่โดยไม่ต้องรอลูกค้ามาบอก ดูคิว เปลี่ยนสถานะการจัดของ ยืนยันจ่ายสินค้า ดูแดชบอร์ดปฏิบัติการ อ่านการแจ้งเตือน | สร้างคำสั่งซื้อ แก้ไขสินค้า ยกเลิกคำสั่งซื้อ ทำเครื่องหมายอ่านการแจ้งเตือน ดูประวัติ และดูแดชบอร์ดระดับบริหารไม่ได้ |
| ผู้จัดการ (Manager) | เจ้าของหรือผู้ดูแลร้าน ต้องเห็นภาพรวมทันทีที่เปิดดู ทำงานแทนพนักงานได้เมื่อคนไม่พอ ทำได้ทุกอย่างของสองบทบาทแรก รวมทั้งจัดการสินค้า ปรับสต็อก ยกเลิกคำสั่งซื้อ ดูแดชบอร์ดทั้งสองระดับ ค้นประวัติ ทำเครื่องหมายอ่านการแจ้งเตือน | ตั้งสถานะส่งมอบสำเร็จโดยตรงไม่ได้ (ต้องผ่านธุรกรรมตัดสต็อก) และแก้ไขหรือลบประวัติที่บันทึกแล้วไม่ได้ |
| ระบบ (System) | ทำสิ่งที่ต้องเกิดเองโดยไม่รอผู้ใช้: ออกเลขที่คำสั่งซื้อ (UC-04) เปลี่ยนสถานะตามผลธุรกรรม ผลักเหตุการณ์ไปหน้าจอ ตรวจเงื่อนไขและสร้างการแจ้งเตือน (UC-11) | ตัดสินใจแทนผู้ใช้ไม่ได้ เช่น ยืนยันรับชำระเงินเองหรือยืนยันจ่ายสินค้าเอง |

ไม่มีบทบาทผู้ดูแลระบบแยกต่างหาก สิทธิ์ดังกล่าวรวมอยู่ในผู้จัดการ เนื่องจากขนาดของร้าน และลูกค้าไม่ใช่ Actor ของระบบตามที่อธิบายใน 2.1

## 2.4 Operating Environment

- ผู้ใช้เข้าถึงระบบผ่านเว็บเบราว์เซอร์ Chrome, Edge หรือ Firefox รุ่นล่าสุด (NFR-07) บนคอมพิวเตอร์ที่จุดชำระเงิน และบนแท็บเล็ตหรือสมาร์ตโฟนที่คลัง ซึ่งหน้าจอคิวและยืนยันจ่ายต้องใช้งานได้ที่ความกว้าง 390 พิกเซล (NFR-03)
- ทุกจุดทำงานอยู่บนเครือข่ายภายในร้านเดียวกัน ระบบหลังบ้านและฐานข้อมูล MySQL 8.0 ติดตั้งบนเครื่องเซิร์ฟเวอร์ภายในร้าน
- บริการพิมพ์ใบเสร็จทำงานบนเครื่องคอมพิวเตอร์หน้าร้านที่ต่อกับเครื่องพิมพ์ Epson TM-T82 ผ่าน USB เท่านั้น จึงเป็นหน่วยติดตั้งแยกจากระบบหลังบ้าน (ตารางที่ 3.17)
- ระบบไม่พึ่งพาบริการภายนอกใดในขณะทำงาน รหัส QR พร้อมเพย์สร้างภายในระบบเอง

## 2.6 User Documentation

- คู่มือพนักงานขาย: ขั้นตอนขาย แสดงรหัส QR ตรวจเงินเข้าจากแอปพลิเคชันธนาคารก่อนกดยืนยัน และสิ่งที่ต้องทำเมื่อใบเสร็จไม่พิมพ์
- คู่มือพนักงานคลังสินค้า: อ่านคิว เปลี่ยนสถานะการจัดของ ยืนยันจ่ายสินค้า และความหมายของข้อความ "ถูกจ่ายไปแล้ว" และ "สต็อกไม่พอ"
- คู่มือผู้จัดการ: จัดการสินค้าและหมวดหมู่ ตั้งจุดสั่งซื้อเพิ่ม ปรับสต็อกพร้อมเหตุผล อ่านแดชบอร์ด การแจ้งเตือน และค้นประวัติ
- คู่มือติดตั้งระบบบนเครื่องใหม่ สำหรับใช้ทวนสอบ NFR-09

หมายเหตุ: คู่มือทั้งสี่รายการยังไม่ได้จัดทำ ณ วันที่ของเอกสารนี้ รูปแบบและช่องทางส่งมอบเป็นการตัดสินใจในขั้นส่งมอบ ไม่ใช่ความต้องการที่ล็อกแล้ว (ดู Appendix C)

# 3. External Interface Requirements

## 3.1 User Interfaces

ส่วนนี้กำหนดลักษณะเชิงตรรกะของหน้าจอเพื่อรองรับความต้องการ โดยอ้างหน้าจอเก้าหน้าตามตารางที่ 3.15 และองค์ประกอบตามตารางที่ 3.21 ของปริญญานิพนธ์ ไม่ล็อกโครงร่างหน้าจอ (Wireframe) หรือไลบรารีส่วนติดต่อผู้ใช้ หลักการที่ใช้กับทุกหน้าจอมีสามข้อตามหัวข้อ 3.9.1 คือ หนึ่งหน้าจอทำงานเดียว การกระทำที่ย้อนกลับไม่ได้ต้องยืนยันซ้ำ และหน้าจอที่ใช้ในคลังต้องใช้ได้บนอุปกรณ์เคลื่อนที่

## 3.4 Communications Interfaces

- **คำขอ-คำตอบ (HTTP/JSON)** — 19 เส้นทางบริการตามตารางที่ 3.18 (ไม่นับเส้นทางตรวจสุขภาพ `/api/health`) ทุกเส้นทางยกเว้นการเข้าสู่ระบบต้องแนบโทเคนในส่วนหัว Authorization และถูกตรวจสิทธิ์ตามบทบาทที่เซิร์ฟเวอร์ก่อนประมวลผล (NFR-01) เส้นทางและบทบาททั้งหมดประกาศในไฟล์เดียว
- **ช่องทางค้าง (Persistent Connection)** — ช่องทางหลักคือ WebSocket ที่ `/ws?token=` ช่องทางสำรองคือ Server-Sent Events ที่ `/api/events` หน้าจอเลือกช่องทางสำรองเองเมื่อช่องทางหลักเปิดไม่ได้ เหตุการณ์ที่ผลักมีสี่ชนิดคือ `order.created`, `order.status`, `order.dispatched` และ `notification.created` ทุกเหตุการณ์ผลักหลังธุรกรรมยืนยันแล้ว (COMMIT) เท่านั้น เพื่อไม่ให้หน้าจอเห็นข้อมูลที่อาจถูกยกเลิก (NFR-02)
- **การเข้ารหัสช่องทาง** — เมื่อติดตั้งใช้งานจริง การเข้าถึงทุกเส้นทางต้องผ่าน HTTPS ตามที่ระบุในแผนภาพบริบท (รูปที่ 3.6) ปัจจุบันยังทำงานบน HTTP ระหว่างพัฒนา (Appendix C)
- **ระบบหลังบ้าน → บริการพิมพ์** — คำขอพิมพ์ส่งภายในเครือข่ายร้านไปยังบริการพิมพ์บนเครื่องหน้าร้าน ระบบหลังบ้านรอผลไม่เกินเวลาที่กำหนด และไม่ส่งซ้ำอัตโนมัติ เพื่อไม่ให้พิมพ์ใบเสร็จซ้ำ

## 4.1 เข้าสู่ระบบและควบคุมสิทธิ์ตามบทบาท — UC-01

| Field | รายละเอียด |

| Goal | ยืนยันตัวตนผู้ใช้ แล้วให้ผู้ใช้เห็นและทำได้เฉพาะสิ่งที่บทบาทของตนมีสิทธิ์ ทั้งที่หน้าจอและที่เซิร์ฟเวอร์ |

### Preconditions
- ผู้ใช้มีบัญชีที่ผู้จัดการสร้างไว้แล้ว และสถานะบัญชีเป็นเปิดใช้งาน

### Success Postconditions
- ผู้ใช้ได้รับโทเคนที่ระบุบทบาท อายุ 8 ชั่วโมง
- ผู้ใช้ถูกพาไปหน้าแรกของบทบาทตน (พนักงานขาย → ขายหน้าร้าน, พนักงานคลัง → คิวรอจ่ายสินค้า, ผู้จัดการ → แดชบอร์ดปฏิบัติการ) และเห็นเฉพาะเมนูของบทบาทนั้น
- ระบบบันทึกเหตุการณ์ LOGIN ลงประวัติการทำรายการพร้อมหมายเลขไอพี

### Main Success Scenario
1. ผู้ใช้กรอกชื่อผู้ใช้และรหัสผ่าน
2. ระบบเปรียบเทียบรหัสผ่านกับค่าที่เข้ารหัสไว้ในฐานข้อมูล
3. ระบบตรวจว่าบัญชียังเปิดใช้งานอยู่
4. ระบบออกโทเคนที่ระบุบทบาทของผู้ใช้ และบันทึก LOGIN ลงประวัติ
5. หน้าจอเก็บโทเคนไว้และพาผู้ใช้ไปหน้าแรกของบทบาท
6. ทุกคำขอหลังจากนี้แนบโทเคน เซิร์ฟเวอร์ตรวจว่าเป็นใคร แล้วตรวจว่าบทบาทนั้นมีสิทธิ์ในเส้นทางที่เรียกหรือไม่ ก่อนประมวลผลทุกครั้ง

2. ผู้จัดการเลือกสินค้าที่ต้องการแก้ไข หรือกดเพิ่มสินค้าใหม่
3. ผู้จัดการแก้ไขข้อมูลแล้วบันทึก ในกรณีปรับยอดคงเหลือ ระบบล็อกแถวสินค้านั้น (FOR UPDATE) ไว้จนจบธุรกรรม เพื่อไม่ให้ชนกับการจ่ายสินค้าที่เกิดพร้อมกัน
4. ระบบบันทึกค่าใหม่ในธุรกรรมเดียวกับการบันทึกประวัติการทำรายการ

| BR-05 | ต้องแจ้งเตือนเชิงรุก ระบบตรวจเงื่อนไขเองหลังทุกครั้งที่สต็อกเปลี่ยน | Mandatory | AC-02, AC-10 |

## 4.3 สร้างคำสั่งซื้อและออกใบเสร็จ — UC-03

กรณีนี้แทนที่การบันทึกการขายด้วยบิลกระดาษที่ไม่มีระบบยืนยัน จึงเป็นจุดที่ตอบวัตถุประสงค์ข้อ 1.2.1 โดยตรง และเป็นจุดเดียวที่คำสั่งซื้อถูกบันทึก (BR-01)

| Priority | Source / Coverage |
|-----------------------|-----------------------------------------------------------------------------|
| High / Must | US-01; FR-03; BR-01; NFR-05; AC-03, AC-05 |

| Field | รายละเอียด |
|-----------------|-----------------------------------------------------------------------------------|
| Goal | บันทึกรายการสินค้าที่ลูกค้าซื้อ คำนวณยอดรวมจากราคาในฐานข้อมูล แสดงรหัส QR พร้อมเพย์ตามยอด และเมื่อยืนยันรับชำระแล้ว บันทึกคำสั่งซื้อ พิมพ์ใบเสร็จ และผลักเข้าคิวคลัง ในการกระทำเดียว |
| Primary Actor | พนักงานขาย (ผู้จัดการทำแทนได้) |
| Supporting Actors | UC-04 (ออกเลขที่คำสั่งซื้อ), บริการพิมพ์ใบเสร็จ, หน้าจอคิวคลังสินค้า |
| Trigger | ลูกค้าเลือกสินค้าที่หน้าร้านและต้องการชำระเงิน |

### Preconditions
- พนักงานขายเข้าสู่ระบบสำเร็จและอยู่ที่หน้าจอขายหน้าร้าน
- ระบบตั้งค่าหมายเลขพร้อมเพย์ของร้านไว้แล้ว

### Success Postconditions
- คำสั่งซื้อถูกบันทึกด้วยสถานะรอจ่ายสินค้า พร้อมเวลารับชำระเงินและผู้สร้าง
- เลขที่คำสั่งซื้อไม่ซ้ำกับคำสั่งซื้อใดในระบบ และรายการสินค้าเก็บราคาต่อหน่วย ณ เวลาที่ขาย
- หน้าจอคิวคลังสินค้าแสดงคำสั่งซื้อใหม่โดยไม่ต้องกดรีเฟรช
- มีบันทึกเหตุการณ์ CREATE_ORDER ในประวัติการทำรายการ

### Main Success Scenario
1. พนักงานเลือกหมวดหมู่หรือค้นหา แล้วแตะสินค้าและระบุจำนวน
2. ระบบดึงราคาปัจจุบันจากฐานข้อมูลมาคำนวณยอดรวม ไม่รับราคาจากหน้าจอ
3. ระบบสร้างและแสดงรหัส QR พร้อมเพย์ตามยอดชำระ
4. ลูกค้าสแกนและโอนเงินผ่านแอปพลิเคชันธนาคาร
5. พนักงานตรวจการแจ้งเตือนเงินเข้าจากแอปพลิเคชันธนาคารแล้วกด "ยืนยันรับชำระเงิน"
6. ระบบเรียก UC-04 เพื่อออกเลขที่คำสั่งซื้อ แล้วบันทึกคำสั่งซื้อ รายการสินค้า และประวัติ ภายในธุรกรรมเดียว
7. หลังธุรกรรมยืนยันแล้ว ระบบสั่งพิมพ์ใบเสร็จและผลักเหตุการณ์ `order.created` ไปยังหน้าจอคิวคลังสินค้า

### Alternate Flows

| ID | เงื่อนไข | การดำเนินการ |
|-------------|------------------------------------|-------------------------------------------------------|
| A1 | ลูกค้าเปลี่ยนใจก่อนชำระเงิน | ไม่มีข้อมูลใดถูกเขียนลงฐานข้อมูล เพราะระบบเขียนแถวเมื่อรับชำระแล้วเท่านั้น ไม่มีสถานะตะกร้า |
| A2 | พนักงานส่งรายการสินค้าเดียวกันซ้ำ | ระบบรวมให้เหลือแถวเดียวโดยบวกจำนวนเข้าด้วยกัน |
| A3 | ราคาสินค้าถูกผู้จัดการแก้ไขระหว่างที่รหัส QR แสดงอยู่ | เมื่อกดยืนยัน ระบบคำนวณยอดใหม่จากราคาปัจจุบันอีกครั้ง คำสั่งซื้อและใบเสร็จใช้ยอดที่บันทึกจริง หากต่างจากยอดที่ลูกค้าโอนมาแล้ว พนักงานเป็นผู้จัดการส่วนต่างหน้าร้าน |

### Exception Flows

| ID | ปัญหา | การตอบสนองของระบบ |
|-------------|--------------------------------|-----------------------------------------------------------|
| E1 | บริการพิมพ์ใบเสร็จขัดข้องหรือปิดอยู่ | คำสั่งซื้อยังถูกบันทึกและเข้าคิวตามปกติ พร้อมคำเตือนบนหน้าจอว่าพิมพ์ไม่สำเร็จ ให้พนักงานสั่งพิมพ์ซ้ำหรือเขียนเลขที่ให้ลูกค้า |
| E2 | สินค้าที่เลือกถูกปิดการขายไปแล้ว | ปฏิเสธด้วยรหัส 400 พร้อมระบุชื่อสินค้ารายการนั้น |
| E3 | ยังไม่ได้ตั้งค่าหมายเลขพร้อมเพย์ของร้าน | ปฏิเสธการคำนวณยอดและสร้างรหัส QR ด้วยรหัส 503 พร้อมชี้ว่าต้องตั้งค่าที่ใด |

| ID | Requirement | Priority | Verification |
|-------------|----------------------------------------------------------------|-------------|-----------------|
| FR-03 | ระบบต้องสร้างคำสั่งซื้อ คำนวณยอด แสดงรหัส QR พร้อมเพย์ ยืนยันรับเงิน สั่งพิมพ์ใบเสร็จ และส่งเข้าคิวเรียลไทม์ทันที | Must | AC-03, AC-04, AC-05 |
| BR-01 | การออกใบเสร็จกระดาษและการส่งคำสั่งซื้อเข้าคิวคลังต้องเกิดจากการกระทำเดียวกัน | Mandatory | AC-03, AC-06 |

## 4.4 สร้างเลขที่คำสั่งซื้อไม่ซ้ำอัตโนมัติ — UC-04

| Priority | Source / Coverage |
|------------------------------|----------------------------------------------------------------------|
| High / Must | US-01; FR-03; NFR-04; AC-04 |

ระบบต้องออกเลขที่คำสั่งซื้อรูปแบบ ORD-YYYYMMDD-NNNN โดยเลขลำดับ NNNN นับต่อเนื่องภายในวัน เลขที่ออกภายในธุรกรรมของ UC-03 เท่านั้น ไม่มีเส้นทางบริการให้ผู้ใช้เรียก และต้องไม่ซ้ำแม้หลายเครื่องยืนยันรับชำระในเวลาเดียวกัน (EV-06 ระบุว่าบิลกระดาษเคยถูกใช้รับของซ้ำ เลขที่ที่ไม่ซ้ำจึงเป็นฐานของการกันซ้ำใน UC-07)

|----------------------------------|-----------------------------------------------|-------------------|
| UC-03 ขั้นที่ 6 เริ่มธุรกรรม | อ่านเลขล่าสุดของวันด้วยการล็อกแถว (FOR UPDATE) เครื่องที่มาพร้อมกันต้องรอคิว แล้วบวกหนึ่ง | ได้เลขถัดไปของวัน |

| สองเครื่องได้เลขเดียวกัน (กรณีขอบ) | ฐานข้อมูลปฏิเสธด้วยข้อจำกัดเลขที่ไม่ซ้ำ ระบบยกเลิกธุรกรรมแล้วลองใหม่ทั้งธุรกรรมโดยอัตโนมัติ | เลขที่ไม่ซ้ำเสมอ ผู้ใช้ไม่รับรู้ |
| ธุรกรรมชนกัน (deadlock หรือรอล็อกนาน) ขณะยังไม่มีเลขของวัน | ลองใหม่ด้วยการหน่วงเวลาแบบสุ่ม | สำเร็จในรอบถัดไป |

|------------------|---------------------------------------------|-------------|-----------------------------|

## 4.5 ดูคิวรอจ่ายสินค้าแบบเรียลไทม์ — UC-05

กรณีนี้ตอบวัตถุประสงค์ข้อ 1.2.2 โดยตรง คลังต้องรู้ว่ามีคำสั่งซื้อรออยู่ก่อนลูกค้าเดินไปถึง (BR-03) จึงต้องผลักข้อมูลจากฝั่งเซิร์ฟเวอร์ ไม่ใช่ให้หน้าจอวนถาม

| Priority | Source / Coverage |
|-----------------------|-----------------------------------------------------------------------------|
| High / Must | US-02; FR-04; BR-03; NFR-02, NFR-03; AC-06 |

| Field | รายละเอียด |
|-----------------|-----------------------------------------------------------------------------------|
| Goal | ให้พนักงานคลังสินค้าเห็นคำสั่งซื้อที่รอจ่ายทันทีที่ลูกค้าชำระเงิน โดยไม่ต้องกดรีเฟรชและไม่ต้องรอลูกค้าเดินมาบอก |
| Primary Actor | พนักงานคลังสินค้า (ผู้จัดการดูได้) |
| Supporting Actors | UC-03 ซึ่งเป็นต้นทางของเหตุการณ์คำสั่งซื้อใหม่ |
| Trigger | พนักงานเปิดหน้าจอคิว หรือเซิร์ฟเวอร์ผลักเหตุการณ์ใหม่มา |

### Preconditions
- พนักงานคลังสินค้าเข้าสู่ระบบและเปิดหน้าจอคิวค้างไว้

### Success Postconditions
- คำสั่งซื้อใหม่ปรากฏบนหน้าจอคิวภายใน 3 วินาที (NFR-02) เรียงตามเวลารับชำระจากเก่าไปใหม่ พร้อมสถานะและเวลารอคอยของแต่ละรายการ
- การเปลี่ยนสถานะหรือการจ่ายสินค้าจากเครื่องใดก็ตาม สะท้อนบนหน้าจอคิวทุกเครื่องที่เปิดอยู่

### Main Success Scenario
1. พนักงานเปิดหน้าจอคิว หน้าจอโหลดรายการคิวปัจจุบันด้วยคำขอครั้งแรก
2. หน้าจอเปิดช่องทางค้างกับเซิร์ฟเวอร์ (WebSocket) แล้วรอเหตุการณ์
3. เมื่อ UC-03 บันทึกคำสั่งซื้อสำเร็จ เซิร์ฟเวอร์ผลักเหตุการณ์ `order.created` หลังธุรกรรมยืนยันแล้ว
4. หน้าจอดึงรายการคิวใหม่และแสดงผล
5. เมื่อมีเหตุการณ์ `order.status` หรือ `order.dispatched` หน้าจอทุกเครื่องอัปเดตพร้อมกัน

### Alternate Flows

| ID | เงื่อนไข | การดำเนินการ |
|-------------|-----------------------------|-------------------------------------------------------------|
| A1 | เปิดช่องทาง WebSocket ไม่สำเร็จ | หน้าจอสลับไปใช้ Server-Sent Events เอง โดยได้รับเหตุการณ์ชุดเดียวกัน |
| A2 | ใช้งานบนสมาร์ตโฟนหรือแท็บเล็ตในคลัง | หน้าจอจัดวางแบบคอลัมน์เดียวที่ความกว้าง 390 พิกเซล ปุ่มสูงไม่น้อยกว่า 44 พิกเซล ไม่มีการเลื่อนแนวนอน (NFR-03) |

### Exception Flows

| ID | ปัญหา | การตอบสนองของระบบ |
|-------------|---------------------------|----------------------------------------------------------------|
| E1 | ช่องทางค้างหลุดเพราะเครือข่ายสะดุด | หน้าจอเชื่อมต่อใหม่เองและโหลดรายการคิวซ้ำ ไม่มีรายการหาย เพราะคิวอ่านจากฐานข้อมูล ไม่ได้ประกอบจากเหตุการณ์ที่อาจพลาดไป |

| ID | Requirement | Priority | Verification |
|-------------|---------------------------------------------------------------------|-------------|-------------|
| FR-04 | ระบบต้องแสดงหน้าจอคิวรอจ่ายสินค้าที่อัปเดตแบบเรียลไทม์ เรียงตามเวลาชำระเงิน | Must | AC-06 |
| BR-03 | ต้องลดระยะเวลารอคอยของลูกค้า คลังต้องรู้คำสั่งซื้อก่อนลูกค้าเดินไปถึง | Mandatory | AC-06 |

## 4.6 ปรับสถานะการจัดของในคิวงาน — UC-06

| Priority | Source / Coverage |
|--------------------------------------|--------------------------------------------------------------|
| Medium / Must | US-02; FR-04; AC-06 |

| Field | รายละเอียด |
|-----------------|-----------------------------------------------------------------------------------|
| Goal | บอกเพื่อนร่วมงานว่าคำสั่งซื้อใบใดมีคนรับไปจัดแล้ว เพื่อไม่ให้สองคนหยิบใบเดียวกัน และถอยกลับได้เมื่อหยิบผิด |
| Primary Actor | พนักงานคลังสินค้า |
| Supporting Actors | ผู้จัดการ (ผู้เดียวที่ยกเลิกคำสั่งซื้อได้) |
| Trigger | พนักงานกด "เริ่มจัดของ" หรือ "ยกเลิกการจัดของ" หรือผู้จัดการกด "ยกเลิกคำสั่งซื้อ" |

### Preconditions
- คำสั่งซื้ออยู่ในสถานะรอจ่ายสินค้าหรือกำลังจัดของ

### Success Postconditions
- สถานะคำสั่งซื้อเปลี่ยนตามลูกศรที่ตารางที่ 3.20 อนุญาต และหน้าจอคิวทุกเครื่องเห็นการเปลี่ยน
- มีบันทึก UPDATE_STATUS (หรือ CANCEL_ORDER) ในประวัติการทำรายการ

### Main Success Scenario
1. พนักงานกด "เริ่มจัดของ" ที่รายการในคิว
2. ระบบตรวจว่าบทบาทของผู้ใช้ตั้งสถานะเป้าหมายนี้ได้
3. ระบบตรวจว่ามีลูกศรจากสถานะปัจจุบันไปสถานะเป้าหมายในแผนภาพสถานะ
4. ระบบเปลี่ยนสถานะและบันทึกประวัติภายในธุรกรรมเดียว
5. หลังธุรกรรมยืนยันแล้ว ระบบผลักเหตุการณ์ `order.status` ไปทุกหน้าจอ

### Alternate Flows

| ID | เงื่อนไข | การดำเนินการ |
|-------------|---------------------------------------------|-----------------------------------------------|
| A1 | พนักงานหยิบผิดใบหรือต้องวางงานกลับ | กด "ยกเลิกการจัดของ" สถานะกลับเป็นรอจ่ายสินค้า สต็อกไม่ถูกแตะ |
| A2 | ผู้จัดการยกเลิกคำสั่งซื้อที่ยังไม่ได้จ่าย (รอจ่ายสินค้าหรือกำลังจัดของ) | สถานะเป็นยกเลิก รายการหายจากคิว สต็อกไม่ถูกแตะ เป็นสถานะปลายทาง |

### Exception Flows

| ID | ปัญหา | การตอบสนองของระบบ |
|-------------|----------------------------------------|----------------------------------------------------|
| E1 | พยายามตั้งสถานะส่งมอบสำเร็จผ่านเส้นทางนี้ | ปฏิเสธด้วยรหัส 400 เส้นทางปรับสถานะทั่วไปไม่รู้จักสถานะนี้ เพราะต้องเกิดผ่านธุรกรรมตัดสต็อกเท่านั้น (CON-05) |
| E2 | พนักงานคลังพยายามยกเลิกคำสั่งซื้อ | ปฏิเสธด้วยรหัส 403 สิทธิ์นี้เป็นของผู้จัดการเท่านั้น |
| E3 | สถานะถูกผู้ใช้อื่นเปลี่ยนไปก่อนแล้ว เช่น อีกเครื่องจ่ายสินค้าไปแล้ว | ปฏิเสธด้วยรหัส 409 พร้อมแจ้งสถานะปัจจุบัน |

| ID | Requirement | Priority | Verification |
|----------------|----------------------------------------------------------------|-------------|-------------|
| FR-04 (ส่วนปรับสถานะ) | ระบบต้องให้ปรับสถานะการจัดของได้เฉพาะตามที่แผนภาพสถานะอนุญาต และตามสิทธิ์ของบทบาท | Must | AC-06 |

## 4.7 ยืนยันจ่ายสินค้าและตัดสต็อก — UC-07

กรณีนี้เป็นความสามารถที่สำคัญที่สุดของระบบ และตอบวัตถุประสงค์ข้อ 1.2.3 โดยตรง ตัวเลขในระบบต้องตรงกับของจริง (BR-02) และบิลเดิมต้องใช้รับของซ้ำไม่ได้ (EV-06)

| Priority | Source / Coverage |
|-------------------------|---------------------------------------------------------------------------|
| Critical / Must | US-03; FR-05, FR-06; BR-02; NFR-04; AC-07, AC-08 |

| Field | รายละเอียด |
|-----------------|-----------------------------------------------------------------------------------|
| Goal | ให้พนักงานคลังสินค้าตรวจของแล้วยืนยันจ่าย โดยระบบตัดสต็อกในธุรกรรมเดียวกัน และรับประกันว่าคำสั่งซื้อหนึ่งรายการถูกจ่ายออกได้เพียงครั้งเดียว |
| Primary Actor | พนักงานคลังสินค้า (ผู้จัดการทำแทนได้) |
| Supporting Actors | UC-11 (ตรวจเงื่อนไขแจ้งเตือนหลังธุรกรรมสำเร็จ) |
| Trigger | พนักงานเลือกคำสั่งซื้อจากคิวและจัดของครบแล้ว |

### Preconditions
- คำสั่งซื้ออยู่ในสถานะรอจ่ายสินค้าหรือกำลังจัดของ

### Success Postconditions
- สถานะคำสั่งซื้อเป็นส่งมอบสำเร็จ พร้อมบันทึกผู้จ่ายและเวลาที่จ่าย
- ยอดคงเหลือของสินค้าทุกรายการลดลงตามจำนวนในคำสั่งซื้อพอดี
- มีบันทึกการเคลื่อนไหวสต็อกหนึ่งแถวต่อสินค้าหนึ่งรายการ พร้อมยอดคงเหลือหลังเปลี่ยน
- คำสั่งซื้อหายจากคิวของทุกหน้าจอ และมีบันทึก CONFIRM_DISPATCH ในประวัติการทำรายการ

### Main Success Scenario
1. พนักงานเปิดรายการจากคิว ระบบแสดงสินค้า จำนวนที่ต้องจัด และยอดคงเหลือปัจจุบันในคลัง
2. พนักงานตรวจของตามรายการ
3. พนักงานกดยืนยัน ระบบถามยืนยันซ้ำอีกครั้ง เพราะการจ่ายย้อนกลับไม่ได้ (หัวข้อ 3.9.1 ข้อสาม)
4. ระบบเริ่มธุรกรรม แล้วเปลี่ยนสถานะคำสั่งซื้อโดยมีเงื่อนไขสถานะเดิม (รอจ่ายสินค้าหรือกำลังจัดของ) อยู่ในคำสั่ง UPDATE เดียวกัน
5. ระบบล็อกแถวสินค้าที่เกี่ยวข้องเรียงตามรหัสสินค้า แล้วหักยอดคงเหลือทีละรายการโดยมีเงื่อนไขว่ายอดต้องเพียงพออยู่ในคำสั่งเดียวกัน
6. ระบบบันทึกการเคลื่อนไหวสต็อกและประวัติการทำรายการ แล้วยืนยันธุรกรรม
7. หลังธุรกรรมสำเร็จ ระบบผลัก `order.dispatched` ให้คำสั่งซื้อหายจากคิวทุกหน้าจอ และตรวจว่าสินค้าใดต่ำกว่าจุดสั่งซื้อเพิ่ม (BR-05)

### Alternate Flows

| ID | เงื่อนไข | การดำเนินการ |
|-------------|----------------------------------------|----------------------------------------------------|
| A1 | คำสั่งซื้ออยู่ในสถานะกำลังจัดของ | ยืนยันจ่ายได้ตามปกติ ตามลูกศรที่แผนภาพสถานะอนุญาต |
| A2 | หลังหักแล้วสินค้าต่ำกว่าจุดสั่งซื้อเพิ่ม | UC-11 สร้างการแจ้งเตือนสินค้าใกล้หมดและผลักไปยังผู้จัดการทันที โดยไม่สร้างซ้ำถ้าใบเดิมยังไม่ได้อ่าน |
| A3 | ยอดคงเหลือปัจจุบันน้อยกว่าจำนวนที่ต้องจ่ายตั้งแต่ก่อนกดยืนยัน | หน้าจอเน้นรายการนั้นและแสดงข้อความ "สต็อกไม่พอ … แจ้งผู้จัดการปรับสต็อกก่อน" พนักงานยังกดยืนยันได้ แต่จะถูกปฏิเสธตาม E2 |

### Exception Flows

| ID | ปัญหา | การตอบสนองของระบบ |
|-------------|----------------------------------|----------------------------------------------------------|
| E1 | คำสั่งซื้อถูกจ่ายไปแล้วโดยเครื่องอื่น | จำนวนแถวที่ถูกแก้ไขในขั้นที่ 4 เป็นศูนย์ ระบบยกเลิกธุรกรรม แล้วแจ้ง "คำสั่งซื้อนี้ถูกจ่ายสินค้าไปแล้ว" ด้วยรหัส 409 ไม่หักสต็อกเพิ่ม |
| E2 | สต็อกไม่เพียงพอสำหรับสินค้ารายการใดรายการหนึ่ง | ยกเลิกธุรกรรมทั้งหมดด้วยรหัส 409 สินค้ารายการที่หักไปแล้วในธุรกรรมย้อนกลับสู่ค่าเดิม สถานะคำสั่งซื้อไม่เปลี่ยน ไม่มีบันทึกการเคลื่อนไหว |
| E3 | ไม่พบคำสั่งซื้อที่ระบุ | ปฏิเสธด้วยรหัส 404 |

| ID | Requirement | Priority | Verification |
|-------------|-------------------------------------------------------------------|-------------|-------------|
| FR-05 | ระบบต้องรับคำขอยืนยันจ่ายสินค้าจากหน้าจอคลังสินค้า โดยต้องยืนยันสองครั้ง และควบคุมลำดับการทำงานของธุรกรรม | Must | AC-07 |
| FR-06 | ระบบต้องดำเนินธุรกรรมตัดสต็อกแบบอะตอมมิก ป้องกันการจ่ายซ้ำ และไม่ให้ยอดคงเหลือติดลบ | Must | AC-07, AC-08 |
| BR-02 | ตัวเลขสินค้าคงเหลือในระบบต้องตรงกับจำนวนสินค้าจริงในคลัง | Mandatory | AC-07, AC-08 |

**กลไกป้องกันการจ่ายซ้ำมีสองชั้น** — ชั้นที่หนึ่ง เงื่อนไขสถานะอยู่ในคำสั่งปรับปรุงข้อมูลเดียวกัน ไม่ได้แยกเป็นการอ่านมาตรวจในโปรแกรมแล้วค่อยเขียน เพราะระหว่างสองขั้นตอนนั้นคำขออื่นแทรกเข้ามาได้ (การล็อกเชิงบวก หัวข้อ 2.1.3) ชั้นที่สอง การล็อกแถวสินค้าตามลำดับรหัสทำให้คำขอที่เข้ามาพร้อมกันต้องรอคิวกันตามลำดับ ไม่เกิดสภาวะแข่งขันและไม่ล็อกไขว้กัน

## 4.8 แสดงแดชบอร์ดปฏิบัติการ — UC-08

กรณีนี้ทำให้ผู้บริหารเห็นสถานการณ์ระหว่างวันแทนการรอสรุปตอนท้ายวัน จึงตอบวัตถุประสงค์ข้อ 1.2.4 โดยตรง

| Priority | Source / Coverage |
|---------------------------------|-------------------------------------------------------------------|
| Medium / Must | US-04; FR-07; BR-04; AC-09 |

| Field | รายละเอียด |
|-----------------|-----------------------------------------------------------------------------------|
| Goal | ให้ผู้จัดการเห็นยอดขายวันนี้ คิวงาน และรายการสินค้าที่ต่ำกว่าจุดสั่งซื้อเพิ่มได้ทันทีที่เปิดหน้าจอ และให้พนักงานคลังเห็นภาพรวมคิวเพื่อวางแผนจัดของ |
| Primary Actor | ผู้จัดการ |
| Supporting Actors | พนักงานคลังสินค้า (เข้าถึงแดชบอร์ดระดับนี้ได้) |
| Trigger | ผู้ใช้เปิดหน้าแดชบอร์ดปฏิบัติการ |

### Preconditions
- ผู้ใช้เข้าสู่ระบบด้วยบทบาทผู้จัดการหรือพนักงานคลังสินค้า

### Success Postconditions
- ตัวเลขที่แสดงตรงกับผลรวมที่คำนวณจากฐานข้อมูลในขณะนั้น

### Main Success Scenario
1. ผู้ใช้เปิดแดชบอร์ดปฏิบัติการ
2. ระบบคำนวณตัวชี้วัดจากฐานข้อมูลโดยตรง ณ เวลาที่เรียก ไม่ใช้ค่าสรุปที่เก็บไว้ล่วงหน้า (BR-04)
3. ระบบแสดงกล่องต้องดูแลวันนี้ไว้บนสุด รวมเรื่องที่ต้องจัดการสามชนิด คือ คำสั่งซื้อที่รอเกินเกณฑ์ สินค้าที่ต่ำกว่าจุดสั่งซื้อเพิ่ม และการแจ้งเตือนที่ยังไม่อ่าน แต่ละเรื่องมีลิงก์ไปหน้าที่ใช้จัดการ ถ้าไม่มีเรื่องใดค้างจะแสดงว่าไม่มีเรื่องต้องดูแล
4. ระบบแสดงยอดขายวันนี้ (ยอดเงินและจำนวนคำสั่งซื้อ) จำนวนคิวรอจ่ายพร้อมเวลารอนานสุด และรายการสินค้าที่ต่ำกว่าจุดสั่งซื้อเพิ่ม เรียงตามที่ขาดมากที่สุดก่อน
5. แดชบอร์ดโหลดข้อมูลใหม่เองเมื่อได้รับเหตุการณ์จากช่องทางค้าง และทุก 60 วินาที

### Alternate Flows

| ID | เงื่อนไข | การดำเนินการ |
|-------------|-----------------------------------|-----------------------------------------------------|
| A1 | พนักงานคลังเปิดแดชบอร์ดปฏิบัติการ | เห็นตัวชี้วัดชุดเดียวกับผู้จัดการ เพื่อวางแผนจัดของ เรื่องสินค้าที่ต่ำกว่าจุดสั่งซื้อเพิ่มในกล่องต้องดูแลวันนี้แสดงโดยไม่มีลิงก์ เพราะหน้าจัดการข้อมูลสินค้าเป็นของผู้จัดการ |

### Exception Flows

| ID | ปัญหา | การตอบสนองของระบบ |
|-------------|-----------------------|------------------------------------------------------------------|
| E1 | ยังไม่มีคำสั่งซื้อในวันนี้ | แสดงยอดศูนย์และข้อความว่ายังไม่มีข้อมูล ไม่แสดงตารางว่างเปล่าโดยไม่อธิบาย |

| ID | Requirement | Priority | Verification |
|----------------|----------------------------------------------------------------|-------------|-------------|
| FR-07 (ระดับปฏิบัติการ) | ระบบต้องแสดงแดชบอร์ดปฏิบัติการที่รวบรวมยอดขายวันนี้ สถานะคิวงาน และระดับสต็อก | Must | AC-09 |
| BR-04 | ผู้บริหารต้องติดตามยอดขายและคิวงานได้ตลอดเวลา ตัวชี้วัดคำนวณสดจากฐานข้อมูล | Mandatory | AC-09 |

## 4.10 ค้นหาและดูประวัติการทำรายการ — UC-10

| Priority | Source / Coverage |
|--------------------------------------|--------------------------------------------------------------|
| Medium / Must | US-06; FR-09; AC-11 |

| Field | รายละเอียด |
|-----------------|-----------------------------------------------------------------------------------|
| Goal | ให้ผู้จัดการตรวจสอบย้อนหลังได้ว่าใครทำอะไร เมื่อใด จากเครื่องไหน และกับข้อมูลรายการใด |
| Primary Actor | ผู้จัดการ |
| Supporting Actors | ทุกโมดูลของระบบซึ่งเป็นผู้บันทึกในธุรกรรมเดียวกับงานที่เกิด |
| Trigger | ผู้จัดการต้องการตรวจสอบเหตุการณ์ย้อนหลัง เช่น เมื่อยอดสต็อกไม่ตรง |

- ผู้จัดการเข้าสู่ระบบสำเร็จ

- ผลลัพธ์ตรงตามเงื่อนไขที่กรองทุกแถว และไม่มีแถวใดถูกแก้ไขหรือลบจากการดู

### Main Success Scenario
1. ผู้จัดการเปิดหน้าประวัติการทำรายการ ระบบแสดงรายการของวันนี้เป็นค่าเริ่มต้น
2. ผู้จัดการกรองตามช่วงวันที่และประเภทการกระทำ (กรองตามผู้กระทำได้ผ่านเส้นทางบริการ)
3. ระบบแสดงผลเรียงจากใหม่ไปเก่า พร้อมชื่อผู้กระทำ การกระทำ ข้อมูลที่ถูกกระทำในรูปที่อ่านออก (เลขที่คำสั่งซื้อพร้อมสรุปรายการสินค้า หรือรหัสและชื่อสินค้า) หมายเลขไอพี และเวลา

### Alternate Flows

| ID | เงื่อนไข | การดำเนินการ |
|-------------|---------------------------------------------|-------------------------------------------|
| A1 | เหตุการณ์ที่ระบบทำเอง เช่น การสร้างการแจ้งเตือน | แสดงผู้กระทำเป็น "ระบบ" ไม่ผูกกับผู้ใช้คนใด |

| ID | ปัญหา | การตอบสนองของระบบ |

| E2 | ระบุประเภทการกระทำที่ไม่มีในรายการที่กำหนด | ปฏิเสธด้วยรหัส 400 |

## 4.11 รับการแจ้งเตือนภายในแอปพลิเคชัน — UC-11

| Priority | Source / Coverage |
|-----------------------------|-----------------------------------------------------------------------|
| Medium / Must | US-05; FR-08; BR-05; AC-10, AC-13 |

ผู้กระทำหลักของกรณีนี้คือระบบอัตโนมัติ ผู้จัดการและพนักงานคลังเป็นผู้รับ ระบบต้องตรวจเงื่อนไขเองหลังทุกครั้งที่สต็อกเปลี่ยน (BR-05) และตามรอบเวลาสำหรับคิวค้าง ไม่รอให้คนมาเปิดดู การแจ้งเตือนเป็นผลของเงื่อนไขที่ตรวจพบ ไม่ใช่สิ่งที่ผู้ใช้สร้างได้เอง

| Stimulus / Condition | System Response | Resulting State |
|----------------------------------|----------------------------------|--------------------------------|
| UC-07 หรือ UC-02 เปลี่ยนยอดคงเหลือสำเร็จ (หลังธุรกรรมยืนยันแล้ว) | ตรวจสินค้าที่ถูกแตะ ถ้าตั้งจุดสั่งซื้อเพิ่มไว้ (มากกว่าศูนย์) และยอดคงเหลือต่ำกว่าจุดนั้น สร้างการแจ้งเตือนสินค้าใกล้หมด ระบุชื่อสินค้า ยอดคงเหลือ และจุดสั่งซื้อเพิ่ม | มีการแจ้งเตือนใหม่ บันทึก CREATE_NOTIFICATION โดยระบบ และผลัก `notification.created` ไปหน้าจอที่เปิดอยู่ |
| สินค้ารายการเดิมมีการแจ้งเตือนที่ยังไม่ได้อ่านอยู่แล้ว | ไม่สร้างซ้ำ เพื่อไม่ให้ผู้จัดการได้รับข้อความเดิมทุกครั้งที่จ่ายสินค้ารายการนั้น | ไม่เปลี่ยน |
| ผู้จัดการทำเครื่องหมายอ่านแล้ว แต่สินค้ายังต่ำกว่าเกณฑ์ และมีการจ่ายสินค้านั้นครั้งถัดไป | สร้างการแจ้งเตือนใหม่ได้ | มีการแจ้งเตือนใบใหม่ |
| ตัวจับเวลาทุก 60 วินาที พบคำสั่งซื้อที่รอจ่ายเกินเกณฑ์ (30 นาที ตั้งค่าได้) | สร้างการแจ้งเตือนคิวงานค้างนานผิดปกติ ระบุเลขที่คำสั่งซื้อและระยะเวลาที่รอ ไม่ซ้ำถ้าใบเดิมยังไม่อ่าน | มีการแจ้งเตือน (AC-13) |
| การสร้างการแจ้งเตือนล้มเหลว | ไม่กระทบธุรกรรมที่ยืนยันไปแล้ว เพราะการตรวจทำนอกธุรกรรม | ข้อมูลหลักถูกต้อง การแจ้งเตือนอาจขาดหนึ่งรอบ |

**ฝั่งผู้รับ** — ผู้จัดการหรือพนักงานคลังเปิดหน้าการแจ้งเตือน ระบบแสดงรายการที่ยังไม่อ่านขึ้นก่อน พร้อมชนิด ข้อความ และเวลา ผู้จัดการกด "อ่านแล้ว" เมื่อรับทราบ ระบบบันทึก READ_NOTIFICATION ลงประวัติ พนักงานคลังอ่านได้แต่ทำเครื่องหมายไม่ได้ (ถูกปฏิเสธด้วยรหัส 403) จำนวนการแจ้งเตือนที่ยังไม่อ่านแสดงเป็นตัวเลขบนเมนูการแจ้งเตือนของทุกหน้าจอ และปรับเองเมื่อได้รับเหตุการณ์ `notification.created` หรือเมื่อผู้จัดการกดอ่านแล้ว

# 6. Other Requirements

## 6.1 Data and Audit Requirements

- ข้อมูลของระบบมีเจ็ดกลุ่ม ได้แก่ ผู้ใช้งาน สินค้า (รวมหมวดหมู่และจุดสั่งซื้อเพิ่ม) คำสั่งซื้อ รายการสินค้าในคำสั่งซื้อ การเคลื่อนไหวสต็อก การแจ้งเตือน และประวัติการทำรายการ ตามตารางที่ 3.19 ของปริญญานิพนธ์ จัดเก็บด้วย InnoDB ทุกตารางเพื่อให้ได้คุณสมบัติ ACID และการล็อกระดับแถว
- คำสั่งซื้อทุกรายการต้องมีเวลารับชำระเงิน ห้ามว่าง เพราะระบบไม่มีสถานะรอชำระเงินและไม่มีตะกร้า (CON-03)
- รายการสินค้าในคำสั่งซื้อต้องเก็บราคาต่อหน่วย ณ เวลาที่ขาย แยกจากราคาปัจจุบันของสินค้า เพื่อให้ใบเสร็จย้อนหลังยังถูกต้องแม้ราคาจะเปลี่ยน
- ทุกการเปลี่ยนแปลงยอดคงเหลือต้องมีบันทึกการเคลื่อนไหวสต็อกพร้อมยอดคงเหลือหลังเปลี่ยนและสาเหตุ (จ่ายตามคำสั่งซื้อ รับสินค้าเข้า หรือปรับตามการนับจริง) ไม่ว่าจะเกิดจากการขายหรือการปรับด้วยมือ
- ประวัติการทำรายการต้องบันทึกผู้กระทำ การกระทำ ชนิดและรหัสของข้อมูลที่ถูกกระทำ หมายเลขไอพี และเวลา ในธุรกรรมเดียวกับงานที่เกิด เป็นบันทึกแบบเพิ่มอย่างเดียว ไม่มีการแก้หรือลบ
- บัญชีผู้ใช้และสินค้าใช้การปิดใช้งานแทนการลบ เพราะคำสั่งซื้อ การเคลื่อนไหว และประวัติที่บันทึกแล้วยังอ้างถึงรายการเหล่านั้น
- ระยะเวลาเก็บรักษาและนโยบายการลบประวัติเมื่อสะสมมากขึ้นยังไม่ได้ตกลงกับเจ้าของร้าน — TBD-05 (Appendix C)

ข้อความเหล่านี้เป็นข้อกำหนดข้อมูลเชิงตรรกะ ไม่ใช่โครงสร้างตาราง ซึ่งอยู่ในปริญญานิพนธ์บทที่ 3 หัวข้อ 3.7

## 6.2 Language and Terminology

- "ยืนยันรับชำระเงิน" ไม่ใช่ "ชำระเงิน" — ระบบไม่ได้รับเงินเอง พนักงานเป็นผู้ยืนยันว่าเห็นเงินเข้าแล้ว ทุกหน้าจอ ข้อความ และเอกสารต้องใช้คำนี้ให้ตรงกัน
- "ส่งมอบสำเร็จ" ใช้เฉพาะเมื่อธุรกรรมตัดสต็อกสำเร็จเท่านั้น ไม่ใช้เป็นคำทั่วไปแทน "จ่ายของแล้ว" เพราะสถานะนี้เป็นหลักฐานว่าสต็อกถูกหักแล้วจริง
- "รับสินค้าเข้า" กับ "ปรับตามการนับจริง" เป็นสาเหตุการเคลื่อนไหวสต็อกคนละชนิด ต้องไม่ใช้ปนกัน อย่างหลังต้องมีหมายเหตุเสมอ
- ชื่อสถานะคำสั่งซื้อทั้งสี่ (รอจ่ายสินค้า กำลังจัดของ ส่งมอบสำเร็จ ยกเลิก) ใช้ตามตารางที่ 3.20 ทุกที่ ทั้งหน้าจอ ประวัติ และเอกสาร
- ส่วนต่อประสานผู้ใช้ ข้อความแจ้งเตือน และใบเสร็จใช้ภาษาไทยทั้งหมด จำนวนเงินแสดงเป็นบาททศนิยมสองตำแหน่ง วันที่บนใบเสร็จแสดงตามปฏิทินไทย (พ.ศ.) ข้อความบนใบเสร็จส่งไปยังเครื่องพิมพ์ด้วยรหัส TIS-620 และหลีกเลี่ยงอักขระที่อยู่นอกชุดรหัสนั้น

# Appendix A: Glossary

| คำศัพท์ | ความหมายในบริบทของระบบนี้ |
|-----------------------------------|-----------------------------------------------------------------|

| คิวรอจ่ายสินค้า (Dispatch Queue) | รายการคำสั่งซื้อที่ชำระเงินแล้วแต่ยังไม่ได้จ่ายสินค้าออกจากคลัง เรียงตามเวลาชำระ |
| การจ่ายสินค้า (Dispatch) | การที่พนักงานคลังยืนยันว่าจ่ายสินค้าตามคำสั่งซื้อออกไปแล้ว ซึ่งตัดสต็อกไปพร้อมกันในธุรกรรมเดียว |
| ตัดสต็อกแบบอะตอมมิก (Atomic Stock Deduction) | การหักยอดคงเหลือที่เกิดขึ้นครบทุกรายการหรือไม่เกิดเลย ไม่มีสภาพครึ่งทาง |
| จุดสั่งซื้อเพิ่ม (Reorder Point) | ยอดคงเหลือที่เมื่อต่ำกว่าค่านี้ ระบบจะแจ้งเตือนให้สั่งซื้อสินค้าเพิ่ม ค่า 0 หมายถึงยังไม่ตั้งและไม่แจ้งเตือน |
| หมวดหมู่สินค้า (Category) | กลุ่มสินค้าตามที่ร้านจัดสต็อกจริง เช่น ปูน เหล็ก สี ประปา ใช้กรองบนหน้าขายและหน้าจัดการสินค้า |
| ธุรกรรม (Transaction) | ชุดคำสั่งฐานข้อมูลที่ถือเป็นหน่วยเดียว สำเร็จทั้งหมดหรือย้อนกลับทั้งหมด |
| ล็อกเชิงบวก (Optimistic Locking) | การใส่เงื่อนไขสถานะเดิมไว้ในคำสั่งปรับปรุงข้อมูล ถ้าสถานะถูกเปลี่ยนไปก่อนแล้วจะไม่มีแถวใดถูกแก้ไข |
| ประวัติการทำรายการ (Audit Log) | บันทึกว่าใครทำอะไรกับข้อมูลใดเมื่อใดจากเครื่องไหน เพิ่มอย่างเดียว ใช้ตรวจสอบย้อนหลัง |
| การเคลื่อนไหวสต็อก (Stock Movement) | บันทึกการเปลี่ยนแปลงยอดคงเหลือหนึ่งครั้ง พร้อมยอดหลังเปลี่ยนและสาเหตุ |
| ช่องทางค้าง (Persistent Connection) | ช่องทางที่เปิดค้างไว้เพื่อให้เซิร์ฟเวอร์ผลักข้อมูลมาหาหน้าจอได้เองโดยหน้าจอไม่ต้องถาม |
| WebSocket | ช่องทางค้างแบบสองทาง ใช้เป็นช่องทางหลักของระบบ |
| SSE (Server-Sent Events) | ช่องทางค้างแบบทางเดียวจากเซิร์ฟเวอร์ไปหน้าจอ ใช้เป็นช่องทางสำรองเมื่อ WebSocket เปิดไม่ได้ |
| พร้อมเพย์ (PromptPay) | บริการโอนเงินผ่านรหัส QR ที่แอปพลิเคชันธนาคารทุกแอปอ่านได้ ระบบสร้างรหัสเองจากหมายเลขร้านและยอดเงิน โดยไม่ต่อกับธนาคาร |
| ESC/POS | ชุดคำสั่งสำหรับสั่งงานเครื่องพิมพ์ใบเสร็จความร้อน |
| TIS-620 | รหัสอักขระไทยที่เครื่องพิมพ์ใบเสร็จเข้าใจ ต้องแปลงจากข้อความก่อนส่ง |
| RBAC (Role-Based Access Control) | การควบคุมสิทธิ์การเข้าถึงตามบทบาทของผู้ใช้ ตรวจที่เซิร์ฟเวอร์ทุกคำขอ |
| ACID | คุณสมบัติสี่ประการของธุรกรรมฐานข้อมูล คือความเป็นหนึ่งเดียว ความคงเส้นคงวา ความเป็นอิสระ และความคงทน |
| ระบบ (System) ในฐานะผู้กระทำ | พฤติกรรมที่เกิดเองโดยไม่มีผู้ใช้กด เช่น ออกเลขที่ ผลักเหตุการณ์ สร้างการแจ้งเตือน ประวัติบันทึกผู้กระทำเป็น "ระบบ" |

## B.1 แบบจำลองวงจรชีวิตของคำสั่งซื้อ

![แผนภาพสถานะของคำสั่งซื้อ](assets/diagrams/fig3-13_state_order.png){width=13cm}

*ภาพที่ 3 — Order Lifecycle Model แสดงสถานะทั้งสี่และเส้นทางการเปลี่ยนสถานะที่ระบบอนุญาต (รูปที่ 3.13 ของปริญญานิพนธ์)*

แบบจำลองนี้เป็นหัวใจของระบบ เพราะสถานะของคำสั่งซื้อทำหน้าที่สองอย่างพร้อมกัน คือบอกว่างานอยู่ขั้นใด และเป็นกลไกล็อกที่ทำให้การจ่ายสินค้าเกิดขึ้นได้เพียงครั้งเดียว สถานะเป็นผลของการกระทำที่บันทึกสำเร็จแล้ว ไม่ใช่ค่าที่ผู้ใช้กำหนดได้โดยตรง ตารางต่อไปนี้สรุปว่าสิ่งเร้าใดทำให้สถานะเปลี่ยนอย่างไร

| Stimulus / Condition | System Response | Resulting State |
|--------------------------------------|----------------------------------------------|----------------|
| ลูกค้ายังไม่ชำระเงิน | ไม่เขียนข้อมูลใดลงฐานข้อมูล | ยังไม่มีคำสั่งซื้อในระบบ |
| พนักงานขายยืนยันรับชำระเงิน (UC-03, UC-04) | ออกเลขที่ไม่ซ้ำ บันทึกคำสั่งซื้อ สั่งพิมพ์ใบเสร็จ และผลักเข้าคิวคลัง | รอจ่ายสินค้า |
| พนักงานคลังกดเริ่มจัดของ (UC-06) | เปลี่ยนสถานะและแจ้งไปยังหน้าจออื่นที่เปิดค้างอยู่ | กำลังจัดของ |
| พนักงานคลังยกเลิกการจัดของ (UC-06) | เปลี่ยนสถานะกลับ สต็อกไม่ถูกแตะ | รอจ่ายสินค้า |
| พนักงานคลังยืนยันจ่ายสินค้าสำเร็จ (UC-07) | หักยอดคงเหลือ บันทึกการเคลื่อนไหวสต็อก และนำออกจากคิว ทั้งหมดในธุรกรรมเดียว | ส่งมอบสำเร็จ |
| เครื่องที่สองยืนยันจ่ายรายการเดิมพร้อมกัน (UC-07 E1) | ปฏิเสธด้วยรหัส 409 พร้อมข้อความว่าถูกจ่ายไปแล้ว ไม่หักสต็อกเพิ่ม | ส่งมอบสำเร็จ (ไม่เปลี่ยน) |
| สินค้ารายการใดรายการหนึ่งมีไม่พอระหว่างธุรกรรม (UC-07 E2) | ย้อนกลับทั้งธุรกรรม ไม่หักสต็อกรายการใดเลย | สถานะเดิม (ไม่เปลี่ยน) |
| ผู้จัดการยกเลิกคำสั่งซื้อที่ยังไม่ได้จ่าย (UC-06 A2) | เปลี่ยนสถานะและนำออกจากคิว พร้อมบันทึกผู้กระทำและเวลา | ยกเลิก |
| ตั้งสถานะส่งมอบสำเร็จผ่านเส้นทางปรับสถานะทั่วไป (UC-06 E1) | ปฏิเสธด้วยรหัส 400 | สถานะเดิม (ไม่เปลี่ยน) |

**Derived-state rule** — สถานะส่งมอบสำเร็จเกิดขึ้นได้ทางเดียวเท่านั้น คือผ่านธุรกรรมตัดสต็อกที่สำเร็จ ระบบต้องปฏิเสธการตั้งค่าสถานะนี้โดยตรง เพราะถ้าอนุญาต สถานะจะไม่ใช่หลักฐานอีกต่อไปว่าสต็อกถูกหักแล้วจริง

## Negative / Boundary Scenarios

- พนักงานคลังสองคนกดยืนยันจ่ายคำสั่งซื้อเดียวกันในเสี้ยววินาทีเดียวกัน → สต็อกถูกหักครั้งเดียว และมีบันทึกการเคลื่อนไหวหนึ่งแถวต่อสินค้าหนึ่งรายการ
- คำสั่งซื้อมีสินค้าสองรายการ รายการแรกมีของพอ รายการที่สองไม่พอ → ยอดของรายการแรกที่หักไปแล้วในธุรกรรมต้องย้อนกลับด้วย ไม่มีการหักค้างบางส่วน
- ผู้ใช้ส่งราคาสินค้ามาพร้อมคำขอเพื่อกำหนดราคาเอง → ระบบใช้ราคาจากฐานข้อมูลเสมอ ค่าที่ส่งมาถูกละเลย
- ผู้จัดการปรับยอดคงเหลือเป็นค่าที่จะทำให้ติดลบ → ปฏิเสธและยอดเดิมไม่เปลี่ยน
- พยายามเปลี่ยนสถานะคำสั่งซื้อเป็นส่งมอบสำเร็จโดยไม่ผ่านธุรกรรมตัดสต็อก → ปฏิเสธด้วยรหัส 400
- ข้อความบนใบเสร็จมีอักขระนอกชุดรหัส TIS-620 → แทนด้วยช่องว่าง ไม่ส่งไบต์แปลกปลอมที่เครื่องพิมพ์อาจตีความเป็นคำสั่งควบคุม
- เปิดหน้าจอคิวบนความกว้าง 390 พิกเซล → รายการแสดงเป็นการ์ดแตะได้ทั้งใบ ปุ่มสูงไม่น้อยกว่า 44 พิกเซล ไม่เกิดการเลื่อนแนวนอนของทั้งหน้า
- คำสั่งซื้อแรกของวันถูกสร้างพร้อมกันจากหลายเครื่อง → ระบบตรวจพบการล็อกชนกัน (deadlock) แล้วขอเลขใหม่อัตโนมัติ ทุกคำขอสำเร็จและเลขไม่ซ้ำ

## E.3 End-to-End Example

ตัวอย่างนี้เดินตามคำสั่งซื้อจริงหนึ่งรายการตั้งแต่ต้นจนจบ เพื่อแสดงว่าความต้องการ กรณีการใช้งาน เกณฑ์การยอมรับ และกรณีทดสอบเชื่อมโยงกันอย่างไรในทางปฏิบัติ

| Step | Scenario | Trace |
|-------------|-----------------------------------------------------------|--------------------------------|
| 1 | ลูกค้าซื้อสีรองพื้น 10 แกลลอนและเหล็กเส้น 4 เส้น พนักงานขายเลือกหมวด "สี" แล้วแตะสินค้า ระบุจำนวน ระบบคำนวณยอดรวมจากราคาในฐานข้อมูล | UC-03; FR-02, FR-03; AC-03 |
| 2 | ระบบสร้างรหัส QR พร้อมเพย์ตามยอดที่คำนวณได้ ลูกค้าสแกนจ่าย พนักงานตรวจการแจ้งเตือนเงินเข้าแล้วกดยืนยันรับชำระเงิน | UC-03; CON-03; ข้อสมมติใน 2.7 |
| 3 | ระบบออกเลขที่คำสั่งซื้อที่ไม่ซ้ำ บันทึกคำสั่งซื้อพร้อมรายการสินค้าในธุรกรรมเดียว สั่งพิมพ์ใบเสร็จ และผลักเหตุการณ์ออกไป | UC-04; FR-03; BR-01; AC-04 |
| 4 | หน้าจอคิวที่คลังสินค้าแสดงคำสั่งซื้อใหม่เองภายในเกณฑ์เวลา โดยพนักงานไม่ต้องกดรีเฟรช พนักงานกดเริ่มจัดของ | UC-05, UC-06; FR-04; NFR-02; AC-06 |
| 5 | พนักงานคลังตรวจของแล้วกดยืนยันจ่ายสองครั้ง ระบบเปลี่ยนสถานะ หักสต็อก และบันทึกการเคลื่อนไหวในธุรกรรมเดียว | UC-07; FR-05, FR-06; NFR-04; AC-07 |
| 6 | พนักงานอีกคนกดยืนยันจ่ายรายการเดิมพร้อมกัน ระบบปฏิเสธด้วยข้อความว่าคำสั่งซื้อถูกจ่ายไปแล้ว และสต็อกไม่ถูกหักซ้ำ | UC-07 E1; BR-02; NFR-04; AC-07 |
| 7 | ยอดคงเหลือของสีรองพื้นต่ำกว่าจุดสั่งซื้อเพิ่ม ระบบสร้างการแจ้งเตือนสินค้าใกล้หมดและแสดงบนหน้าจอผู้จัดการทันที | UC-11; FR-08; BR-05; AC-10 |
| 8 | ผู้จัดการเปิดแดชบอร์ดเห็นยอดขายและคิวงานที่คำนวณสดจากฐานข้อมูล และค้นหาประวัติย้อนหลังของคำสั่งซื้อรายการนี้ได้ครบทุกเหตุการณ์ (สร้าง เปลี่ยนสถานะ จ่าย) | UC-08, UC-10; FR-07, FR-09; AC-09, AC-11 |
