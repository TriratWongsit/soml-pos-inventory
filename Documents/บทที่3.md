## 3.1 กระบวนการดำเนินงานโครงงาน

การดำเนินโครงงานนี้ถูกออกแบบให้เป็นขั้นตอนเชิงวิศวกรรมซอฟต์แวร์ เพื่อให้กระบวนการพัฒนามีความเป็นระบบและสามารถตรวจสอบความก้าวหน้าได้อย่างต่อเนื่อง โดยแบ่งออกเป็น 6 ระยะสำคัญตามแผนการดำเนินงานในตารางที่ 1.1 ได้แก่ ระยะวิเคราะห์ความต้องการ ระยะออกแบบระบบ ระยะพัฒนาโมดูลหลักระยะที่ 1 ระยะพัฒนาโมดูลหลักระยะที่ 2 ระยะพัฒนาแดชบอร์ดและระบบแจ้งเตือน และระยะทดสอบและประเมินผล ดังแสดงในรูปที่ 3.1

![กระบวนการดำเนินงานโครงงาน](assets/diagrams/fig3-01_process.png)

**รูปที่ 3.1** กระบวนการดำเนินงานโครงงาน

จากรูปที่ 3.1 กระบวนการดำเนินงานถูกจัดเรียงแบบต่อเนื่องโดยผลลัพธ์ของแต่ละระยะเป็นข้อมูลนำเข้าของระยะถัดไป การแบ่งการพัฒนาโมดูลหลักออกเป็นสองระยะช่วยให้ทีมงานสามารถส่งมอบระบบต้นแบบที่ใช้งานได้บางส่วนตั้งแต่เดือนที่ 3 และนำไปทดลองใช้ที่หน้าร้านเพื่อรับข้อเสนอแนะกลับมาปรับปรุงก่อนพัฒนาส่วนคลังสินค้าในเดือนที่ 4 ซึ่งช่วยลดความเสี่ยงจากการพบข้อผิดพลาดเชิงออกแบบในช่วงท้ายของโครงงาน

### 3.1.1 ระยะวิเคราะห์ความต้องการ

เป็นการสำรวจปัญหาหน้างานจริง (Pain Points) ที่ร้านวัสดุก่อสร้างอำพรคอนกรีต สัมภาษณ์พนักงานขาย พนักงานคลังสินค้า และผู้จัดการ เพื่อทำความเข้าใจกระบวนการทำงานเดิมที่อาศัยเอกสารกระดาษ จากนั้นนำข้อมูลที่ได้มากำหนดความต้องการทางธุรกิจ (BR) ความต้องการเชิงหน้าที่ (FR) และความต้องการเชิงคุณภาพ (NFR) พร้อมจัดลำดับความสำคัญของความต้องการด้วยวิธี MoSCoW และตกลงขอบเขตการทำงานร่วมกับสถานประกอบการ ผลลัพธ์ของระยะนี้คือเอกสารข้อกำหนดความต้องการของซอฟต์แวร์ (SRS) และเอกสาร SE-02

### 3.1.2 ระยะออกแบบระบบ

เป็นการแปลงความต้องการที่รวบรวมไว้ให้เป็นแบบที่พัฒนาได้จริง ประกอบด้วยการออกแบบสถาปัตยกรรมระบบด้วย C4 Model ทั้งระดับบริบท ระดับคอนเทนเนอร์ และระดับส่วนประกอบ การออกแบบกรณีการใช้งาน (Use Case) การออกแบบโครงสร้างฐานข้อมูลเชิงสัมพันธ์ (ERD) การออกแบบแผนภาพลำดับและแผนภาพกิจกรรมสำหรับกระบวนการหลัก และการออกแบบต้นแบบส่วนติดต่อผู้ใช้ทั้งสามบทบาท ผลลัพธ์ของระยะนี้คือเอกสารการออกแบบระบบและต้นแบบหน้าจอ

### 3.1.3 ระยะพัฒนาโมดูลหลักระยะที่ 1

เป็นการพัฒนาส่วนที่เกี่ยวข้องกับหน้าร้าน เริ่มจากระบบลงชื่อเข้าใช้งานและการควบคุมสิทธิ์ตามบทบาท การจัดการข้อมูลสินค้าหลักและการตั้งค่าจุดสั่งซื้อเพิ่ม ระบบสร้างคำสั่งซื้อและคำนวณยอดรวมอัตโนมัติ การสร้างรหัส QR พร้อมเพย์ตามยอดชำระ และการเชื่อมต่อเครื่องพิมพ์ใบเสร็จความร้อนผ่านโพรโทคอล ESC/POS

### 3.1.4 ระยะพัฒนาโมดูลหลักระยะที่ 2

เป็นการพัฒนาส่วนที่เกี่ยวข้องกับคลังสินค้า ได้แก่ ระบบผลักข้อมูลคำสั่งซื้อไปยังหน้าจอคิวงานแบบเรียลไทม์ หน้าจอคิวรอจ่ายสินค้าที่อัปเดตอัตโนมัติ ฟังก์ชันเลือกคำสั่งซื้อและยืนยันจ่ายสินค้าพร้อมตัดสต็อกแบบอะตอมมิก กลไกป้องกันการยืนยันจ่ายซ้ำ และระบบบันทึกประวัติการทำรายการ

### 3.1.5 ระยะพัฒนาแดชบอร์ดและระบบแจ้งเตือน

เป็นการพัฒนาส่วนสนับสนุนการตัดสินใจของผู้จัดการ ประกอบด้วยแดชบอร์ดปฏิบัติการที่รวบรวมสถิติยอดขาย ระดับสต็อก และสถานะคิวงานแบบเรียลไทม์ ระบบตรวจสอบจุดสั่งซื้อเพิ่มโดยอัตโนมัติ และระบบแจ้งเตือนภายในแอปพลิเคชันเมื่อสต็อกต่ำกว่าเกณฑ์หรือมีคิวงานค้างนานผิดปกติ ผลลัพธ์ของระยะนี้คือระบบเวอร์ชันสมบูรณ์ (Alpha Release)

### 3.1.6 ระยะทดสอบและประเมินผล

เป็นการตรวจสอบระบบตามแผนการทดสอบในหัวข้อ 3.9 ครอบคลุมการทดสอบความถูกต้องเชิงฟังก์ชัน การทดสอบประสิทธิภาพ การทดสอบความสอดคล้องของข้อมูลสต็อก และการทดสอบการยอมรับจากผู้ใช้งานจริงในสถานประกอบการ พร้อมทั้งรวบรวมผลการทดสอบและจัดทำรูปเล่มโครงงานฉบับสมบูรณ์

## 3.2 ภาพรวมสถาปัตยกรรมของระบบ

ระบบ SOML ออกแบบตามสถาปัตยกรรมซอฟต์แวร์แบบ 3 ชั้น (3-Tier Architecture) ตามหลักการแยกส่วนประกอบ (Separation of Concerns) ที่อธิบายไว้ในหัวข้อ 2.1.1 โดยแบ่งความรับผิดชอบออกเป็นชั้นการนำเสนอข้อมูลซึ่งพัฒนาด้วย React.js ในรูปแบบ Responsive Web Application ชั้นตรรกะทางธุรกิจซึ่งพัฒนาด้วย Node.js ร่วมกับ Express.js ทำหน้าที่ควบคุมสิทธิ์ ประมวลผลคำสั่งซื้อ ตัดสต็อก และผลักข้อมูลแบบเรียลไทม์ และชั้นข้อมูลซึ่งใช้ฐานข้อมูลเชิงสัมพันธ์ MySQL 8.0 บนกลไกจัดเก็บ InnoDB เพื่อรองรับคุณสมบัติ ACID

การอธิบายสถาปัตยกรรมในบทนี้ใช้ C4 Model ของ Simon Brown ตามที่กล่าวไว้ในหัวข้อ 2.1.2 โดยเริ่มจากระดับบริบทของระบบ (Context) ซึ่งแสดงความสัมพันธ์ระหว่างระบบกับผู้ใช้งานและระบบภายนอก ดังรายละเอียดในตารางที่ 3.1

**ตารางที่ 3.1** องค์ประกอบในแผนภาพบริบทของระบบ

| องค์ประกอบ | ประเภท | หน้าที่ |
|---|---|---|
| พนักงานขาย (Sales Staff) | Person | บันทึกคำสั่งซื้อ แสดง QR พร้อมเพย์ ยืนยันรับชำระเงิน และสั่งพิมพ์ใบเสร็จ |
| พนักงานคลังสินค้า (Warehouse Worker) | Person | ดูคิวรอจ่ายสินค้าแบบเรียลไทม์ ยืนยันจ่ายสินค้า และตัดสต็อก |
| ผู้จัดการ (Manager) | Person | ดูแดชบอร์ด จัดการข้อมูลสินค้าและผู้ใช้งาน ตรวจสอบประวัติการทำรายการ และรับการแจ้งเตือน |
| ระบบ SOML | Software System | ระบบหลักที่พัฒนาขึ้นในโครงงานนี้ เป็นเว็บแอปพลิเคชันแบบ 3 ชั้น |
| PromptPay QR Library | External System | ไลบรารีสร้างรหัส QR ตามมาตรฐาน EMVCo Merchant-Presented Mode |
| เครื่องพิมพ์ใบเสร็จความร้อน | External Hardware | อุปกรณ์ต่อพ่วงที่รับคำสั่ง ESC/POS จากระบบเพื่อพิมพ์ใบเสร็จกระดาษ |

![แผนภาพบริบทของระบบ](assets/diagrams/fig3-02_c1_context.png)

**รูปที่ 3.2** แผนภาพบริบทของระบบ (C1: System Context Diagram)

จากรูปที่ 3.2 ผู้ใช้งานทั้งสามบทบาทเข้าถึงระบบผ่านเว็บเบราว์เซอร์ด้วยโพรโทคอล HTTPS เพียงช่องทางเดียว ทำให้ไม่ต้องติดตั้งโปรแกรมเพิ่มเติมบนเครื่องผู้ใช้ ระบบเชื่อมต่อกับองค์ประกอบภายนอกเพียงสองส่วนคือไลบรารีสร้างรหัส QR พร้อมเพย์และเครื่องพิมพ์ใบเสร็จความร้อน จะเห็นได้ว่าระบบไม่มีการเชื่อมต่อกับ Payment Gateway หรือ API ของธนาคารเพื่อตรวจสอบสถานะการชำระเงินอัตโนมัติ ซึ่งสอดคล้องกับขอบเขตที่กำหนดไว้ในหัวข้อ 1.3.6 โดยพนักงานขายเป็นผู้ตรวจสอบและยืนยันการรับเงินด้วยตนเองจากการแจ้งเตือนของแอปพลิเคชันธนาคาร

## 3.3 การออกแบบระดับคอนเทนเนอร์

เมื่อขยายรายละเอียดจากระดับบริบทลงมาอีกหนึ่งชั้น จะเห็นองค์ประกอบที่สามารถติดตั้งและทำงานได้อย่างอิสระภายในขอบเขตของระบบ SOML ซึ่งเรียกว่าคอนเทนเนอร์ (Container) ตามนิยามของ C4 Model โดยแต่ละคอนเทนเนอร์และเทคโนโลยีที่เลือกใช้แสดงในตารางที่ 3.2

**ตารางที่ 3.2** คอนเทนเนอร์และเทคโนโลยีที่ใช้ในระบบ

| คอนเทนเนอร์ | เทคโนโลยี | หน้าที่ |
|---|---|---|
| Web Application (Frontend) | React.js | ส่วนติดต่อผู้ใช้แบบ Responsive Design ครอบคลุมหน้าจอขายหน้าร้าน หน้าจอคิวคลังสินค้า และแดชบอร์ดปฏิบัติการ |
| Backend API | Node.js + Express.js | ประมวลผลตรรกะทางธุรกิจ ควบคุมสิทธิ์ตามบทบาท ตัดสต็อกแบบอะตอมมิก และผลักข้อมูลแบบเรียลไทม์ |
| Database | MySQL 8.0 (InnoDB) | จัดเก็บข้อมูลผู้ใช้งาน สินค้า คำสั่งซื้อ การเคลื่อนไหวสต็อก การแจ้งเตือน และประวัติการทำรายการ |
| Receipt Print Service | Node.js + ESC/POS | รับคำสั่งพิมพ์จาก Backend API และส่งต่อไปยังเครื่องพิมพ์ใบเสร็จความร้อน |
| PromptPay QR Module | ไลบรารีสร้าง QR Code | สร้างรหัส QR ตามมาตรฐาน EMVCo ให้ตรงกับยอดชำระของแต่ละคำสั่งซื้อ |

![แผนภาพคอนเทนเนอร์](assets/diagrams/fig3-03_c2_container.png)

**รูปที่ 3.3** แผนภาพคอนเทนเนอร์ของระบบ (C2: Container Diagram)

จากรูปที่ 3.3 การสื่อสารระหว่างส่วนหน้าเว็บกับระบบหลังบ้านใช้สองช่องทางที่ทำงานคู่กัน ช่องทางแรกคือ REST API สำหรับคำขอที่ผู้ใช้งานเป็นฝ่ายเริ่ม เช่น การสร้างคำสั่งซื้อหรือการยืนยันจ่ายสินค้า และช่องทางที่สองคือ WebSocket สำหรับให้ระบบหลังบ้านเป็นฝ่ายผลักข้อมูลไปยังหน้าจอคิวคลังสินค้าเมื่อมีคำสั่งซื้อใหม่เข้ามา ตามแนวคิดการสื่อสารแบบขับเคลื่อนด้วยเหตุการณ์ในหัวข้อ 2.1.5 การออกแบบเช่นนี้ทำให้พนักงานคลังสินค้าไม่จำเป็นต้องกดรีเฟรชหน้าจอ และทำให้ระบบตอบสนองได้ภายในเวลาที่กำหนดไว้ใน NFR-02 คือไม่เกิน 3 วินาที

นอกจากนี้ การแยกบริการพิมพ์ใบเสร็จออกเป็นคอนเทนเนอร์ต่างหากช่วยให้ระบบหลังบ้านไม่ถูกบล็อกการทำงานขณะรอผลการพิมพ์จากอุปกรณ์ต่อพ่วง และทำให้สามารถเปลี่ยนรุ่นหรือยี่ห้อเครื่องพิมพ์ในอนาคตได้โดยแก้ไขเฉพาะบริการนี้เพียงส่วนเดียว

## 3.4 การออกแบบส่วนประกอบภายในระบบหลังบ้าน

ภายในคอนเทนเนอร์ Backend API ถูกแบ่งออกเป็นส่วนประกอบย่อยตามความรับผิดชอบ เพื่อให้แต่ละส่วนมีหน้าที่เดียวที่ชัดเจนและทดสอบได้อย่างอิสระ รายละเอียดของแต่ละส่วนประกอบแสดงในตารางที่ 3.3

**ตารางที่ 3.3** ส่วนประกอบภายในระบบหลังบ้าน

| ส่วนประกอบ | หน้าที่ | ความต้องการที่รองรับ |
|---|---|---|
| Auth Controller | ตรวจสอบการเข้าสู่ระบบ ออกโทเคน JWT และตรวจสอบบทบาทของผู้ใช้งานก่อนเข้าถึงทรัพยากร | FR-01 |
| Product Controller | เพิ่ม แก้ไข ลบ และค้นหาข้อมูลสินค้า รวมถึงการตั้งค่าจุดสั่งซื้อเพิ่ม | FR-02 |
| Order Controller | สร้างเลขที่คำสั่งซื้อไม่ซ้ำ คำนวณยอดรวม บันทึกคำสั่งซื้อ และเรียกใช้โมดูลสร้าง QR | FR-03 |

### 3.5.3 ธุรกรรมการตัดสต็อกแบบอะตอมมิกและการป้องกันการจ่ายซ้ำ

จุดที่อ่อนไหวที่สุดของระบบคือขั้นตอนการยืนยันจ่ายสินค้า เนื่องจากอาจเกิดกรณีที่พนักงานคลังสินค้าสองคนกดยืนยันจ่ายคำสั่งซื้อเดียวกันในเวลาไล่เลี่ยกัน หรือกรณีที่ลูกค้านำใบเสร็จเดิมกลับมารับสินค้าซ้ำ ซึ่งเป็นปัญหาที่ระบุไว้ตั้งแต่หัวข้อ 1.1 ระบบจึงออกแบบให้การตัดสต็อกทำงานภายในธุรกรรมเดียวที่มีคุณสมบัติอะตอมมิก โดยใช้เงื่อนไขสถานะของคำสั่งซื้อทำหน้าที่เป็นกลไกล็อกในตัว ดังนี้

```sql
START TRANSACTION;

  UPDATE orders
     SET status = 'delivered', dispatched_by = :user_id, dispatched_at = NOW()
   WHERE order_id = :order_id AND status = 'awaiting_dispatch';
  -- ตรวจสอบจำนวนแถวที่ถูกแก้ไข ถ้าเท่ากับ 0 แสดงว่าคำสั่งซื้อถูกจ่ายไปแล้ว

  SELECT product_id, qty FROM order_items WHERE order_id = :order_id FOR UPDATE;

  UPDATE products
     SET stock_qty = stock_qty - :qty
   WHERE product_id = :product_id AND stock_qty >= :qty;
  -- ตรวจสอบจำนวนแถวที่ถูกแก้ไข ถ้าเท่ากับ 0 แสดงว่าสต็อกไม่เพียงพอ

  INSERT INTO stock_movements
    (product_id, order_id, change_qty, balance_after, reason, created_by)
  VALUES (:product_id, :order_id, -:qty, :balance_after, 'sale_dispatch', :user_id);

  INSERT INTO audit_logs (user_id, action, entity_type, entity_id, detail)
  VALUES (:user_id, 'CONFIRM_DISPATCH', 'order', :order_id, :detail_json);

COMMIT;
```

หลักการสำคัญอยู่ที่เงื่อนไข `AND status = 'awaiting_dispatch'` ในคำสั่ง `UPDATE` แรก ซึ่งทำให้การเปลี่ยนสถานะสำเร็จได้เพียงครั้งเดียวเท่านั้น หากมีคำขอที่สองเข้ามาหลังจากคำขอแรกทำสำเร็จไปแล้ว จำนวนแถวที่ถูกแก้ไขจะเป็นศูนย์ ระบบจะยกเลิกธุรกรรมทั้งหมดด้วยคำสั่ง `ROLLBACK` และแจ้งพนักงานว่าคำสั่งซื้อนี้ถูกจ่ายสินค้าไปแล้ว วิธีการนี้เรียกว่าการล็อกแบบมองโลกในแง่ดี (Optimistic Locking) ผ่านเงื่อนไขสถานะ ซึ่งมีข้อดีคือไม่ต้องถือล็อกไว้ตั้งแต่ตอนที่พนักงานเปิดดูรายการสินค้า จึงไม่กีดขวางการทำงานของพนักงานคนอื่นในระหว่างนั้น

การใช้ `SELECT ... FOR UPDATE` กับตาราง `order_items` ทำให้แถวของสินค้าที่เกี่ยวข้องถูกล็อกไว้จนกว่าธุรกรรมจะสิ้นสุด ป้องกันภาวะ Race Condition เมื่อมีคำสั่งซื้อหลายรายการที่มีสินค้าชนิดเดียวกันถูกยืนยันจ่ายพร้อมกัน ส่วนเงื่อนไข `AND stock_qty >= :qty` ในการหักสต็อกเป็นการป้องกันชั้นสุดท้ายไม่ให้ยอดคงเหลือติดลบ การออกแบบทั้งหมดนี้สอดคล้องกับสมมติฐานที่ตั้งไว้ในหัวข้อ 1.4.2 และ 1.4.3 ของบทที่ 1

เมื่อธุรกรรมสำเร็จแล้ว ระบบจะเรียก Alert Engine เพื่อตรวจสอบว่ายอดคงเหลือของสินค้าที่เพิ่งถูกตัดต่ำกว่าจุดสั่งซื้อเพิ่มหรือไม่ หากต่ำกว่าจะบันทึกการแจ้งเตือนลงตาราง `notifications` การแยกขั้นตอนนี้ออกมาทำนอกธุรกรรมหลักเป็นการจงใจ เพื่อไม่ให้ความล่าช้าของการแจ้งเตือนไปยืดเวลาการถือล็อกฐานข้อมูล

### 3.6.2 คำอธิบายกรณีการใช้งาน

**ตารางที่ 3.12** คำอธิบาย UC-01 เข้าสู่ระบบและควบคุมสิทธิ์ตามบทบาท

| หัวข้อ | รายละเอียด |

| Actor(s) | พนักงานขาย, พนักงานคลังสินค้า, ผู้จัดการ |
| Description | ผู้ใช้งานเข้าสู่ระบบด้วยชื่อผู้ใช้และรหัสผ่าน ระบบตรวจสอบตัวตนแล้วกำหนดเมนูและสิทธิ์การเข้าถึงข้อมูลตามบทบาทของผู้ใช้งานรายนั้น |

| Main Flow | 1) ผู้ใช้งานกรอกชื่อผู้ใช้และรหัสผ่าน 2) ระบบเปรียบเทียบรหัสผ่านกับค่าที่เข้ารหัสไว้ในตาราง users 3) ระบบออกโทเคน JWT ที่ระบุบทบาทของผู้ใช้งาน 4) ระบบแสดงเมนูตามบทบาทที่ตรวจสอบได้ |

จากรูปที่ 3.10 จุดสำคัญของกระบวนการอยู่ที่ขั้นตอนที่พนักงานกดยืนยันรับชำระเงิน เนื่องจากเป็นจุดที่ระบบดำเนินการสามอย่างต่อเนื่องกัน คือเปลี่ยนสถานะคำสั่งซื้อเป็นรอจ่ายสินค้า สั่งพิมพ์ใบเสร็จ และผลักเหตุการณ์ไปยังหน้าจอคิวคลังสินค้า จะสังเกตได้ว่าลูกค้ายังไม่ได้เดินไปถึงคลังสินค้าในขณะนั้น แต่พนักงานคลังเห็นคำสั่งซื้อบนหน้าจอแล้ว ซึ่งเป็นกลไกหลักที่ทำให้เกิดการลดระยะเวลารอคอยตามวัตถุประสงค์ข้อ 1.2.2

นอกจากนี้ การเรียกใช้บริการพิมพ์ใบเสร็จและการผลักข้อมูลเข้าคิวถูกออกแบบให้ทำงานเป็นอิสระจากกัน หากขั้นตอนใดขั้นตอนหนึ่งล่าช้า อีกขั้นตอนหนึ่งจะไม่ถูกหน่วงตามไปด้วย ทำให้ระบบสามารถรักษาเกณฑ์เวลาตอบสนองไม่เกิน 3 วินาทีตาม NFR-02 ไว้ได้แม้เครื่องพิมพ์จะทำงานช้ากว่าปกติ

## 3.8 การออกแบบส่วนติดต่อผู้ใช้

### 3.8.1 หลักการออกแบบ

ส่วนติดต่อผู้ใช้ของระบบ SOML ออกแบบตามหลักปฏิสัมพันธ์ระหว่างมนุษย์กับคอมพิวเตอร์ที่กล่าวไว้ในหัวข้อ 2.1.9 โดยยึดหลักสามข้อ ข้อแรกคือความเรียบง่าย แต่ละหน้าจอมีงานหลักเพียงงานเดียวและวางปุ่มของงานนั้นให้เด่นที่สุด ข้อที่สองคือความชัดเจนของข้อมูล ตัวเลขที่สำคัญต่อการตัดสินใจถูกแสดงด้วยขนาดใหญ่และจัดชิดขวาเพื่อให้เปรียบเทียบกันได้ง่าย และข้อที่สามคือการยืนยันก่อนดำเนินการที่ส่งผลถาวรต่อข้อมูล

ระบบใช้สีอย่างสม่ำเสมอในความหมายเดียวกันทั่วทั้งระบบ ได้แก่ สีน้ำเงินสำหรับปุ่มดำเนินการทั่วไป สีเขียวสำหรับสถานะปกติและปุ่มยืนยันที่ทำให้ธุรกรรมสมบูรณ์ สีส้มสำหรับสถานะที่ต้องเฝ้าระวัง เช่น คำสั่งซื้อที่รอจ่ายหรือสต็อกที่ใกล้ถึงจุดสั่งซื้อเพิ่ม และสีแดงสำหรับสถานะที่ต้องดำเนินการทันที เช่น สต็อกที่ต่ำกว่าจุดสั่งซื้อแล้วหรือคำสั่งซื้อที่รอนานผิดปกติ การกำหนดความหมายของสีไว้ล่วงหน้าเช่นนี้ช่วยให้พนักงานที่ไม่คุ้นเคยกับเทคโนโลยีสามารถประเมินสถานการณ์ได้จากสีก่อนที่จะอ่านข้อความ

ส่วนขวาเป็นรายการแจ้งเตือนภายในแอปพลิเคชันและประวัติการทำรายการล่าสุด การวางสองส่วนนี้ไว้ในหน้าเดียวกับตัวชี้วัดหลัก ทำให้ผู้จัดการสามารถตรวจสอบทั้งสถานการณ์ปัจจุบันและเหตุการณ์ที่เพิ่งเกิดขึ้นได้โดยไม่ต้องสลับหน้าจอ ซึ่งตอบวัตถุประสงค์ข้อ 1.2.4 เรื่องการติดตามสถานะแบบเรียลไทม์เพื่อการตัดสินใจจากข้อมูลจริง

### 3.8.5 การรองรับอุปกรณ์เคลื่อนที่

![หน้าจอคิวรอจ่ายสินค้าบนอุปกรณ์เคลื่อนที่](assets/mockups/fig3-19_queue_mobile.png)

**รูปที่ 3.19** หน้าจอคิวรอจ่ายสินค้าในโหมดอุปกรณ์เคลื่อนที่

จากรูปที่ 3.19 เมื่อความกว้างหน้าจอลดลงถึงระดับสมาร์ตโฟน ระบบจะเปลี่ยนการแสดงผลจากตารางเป็นรายการแบบการ์ดซ้อนกันในแนวตั้ง เนื่องจากตารางที่มีหลายคอลัมน์ไม่สามารถอ่านได้สะดวกบนหน้าจอแคบ แต่ละการ์ดยังคงแสดงข้อมูลครบถ้วนเหมือนแถวในตาราง ได้แก่ เลขที่คำสั่งซื้อ เวลารอ รายการสินค้า สถานะ และปุ่มเปิดรายการ นอกจากนี้แถบสีทางซ้ายของการ์ดยังทำหน้าที่สื่อความเร่งด่วนแทนสีของตัวเลขเวลารอในโหมดตาราง

การออกแบบเช่นนี้ตอบความต้องการเชิงคุณภาพ NFR-03 ที่กำหนดให้หน้าจอคิวและยืนยันจ่ายรองรับการใช้งานบนแท็บเล็ตและสมาร์ตโฟนได้สะดวก ซึ่งมีความสำคัญในทางปฏิบัติ เพราะพนักงานคลังสินค้าต้องเดินไปมาระหว่างชั้นวางสินค้าและไม่สามารถอยู่หน้าคอมพิวเตอร์ตั้งโต๊ะได้ตลอดเวลา

## 3.9 แผนการทดสอบระบบ

เพื่อให้มั่นใจว่าระบบที่พัฒนาขึ้นทำงานได้ถูกต้อง มีเสถียรภาพ และเป็นที่ยอมรับของผู้ใช้งานจริง จึงได้วางแผนการทดสอบอย่างเป็นระบบ โดยแบ่งออกเป็น 4 ระดับตามลำดับจากส่วนย่อยไปสู่ภาพรวม ดังแสดงในตารางที่ 3.23

**ตารางที่ 3.23** ระดับการทดสอบระบบ

| ระดับการทดสอบ | วัตถุประสงค์ | ขอบเขตการทดสอบ | เครื่องมือที่ใช้ | เกณฑ์การผ่าน |
|---|---|---|---|---|
| Unit Testing | ตรวจสอบความถูกต้องของฟังก์ชันย่อย | การคำนวณยอดรวม การสร้างเลขที่คำสั่งซื้อ การเข้ารหัสรหัสผ่าน การตรวจสอบสิทธิ์ตามบทบาท | Jest | ทุกกรณีทดสอบผ่าน และครอบคลุมโค้ดไม่น้อยกว่าร้อยละ 70 |
| Integration Testing | ตรวจสอบการทำงานร่วมกันระหว่างส่วนประกอบ | เส้นทาง REST API ครบทุกจุด การทำงานร่วมกันของ Dispatch Controller กับ Stock Deduction Service การเชื่อมต่อฐานข้อมูล | Jest + Supertest | ทุกเส้นทาง API ตอบสถานะและข้อมูลถูกต้อง |
| System Testing | ตรวจสอบระบบทั้งหมดตามกรณีการใช้งาน | UC-01 ถึง UC-11 การผลักข้อมูลผ่าน WebSocket การพิมพ์ใบเสร็จ การตัดสต็อกพร้อมกัน | ทดสอบด้วยมือตามสคริปต์ทดสอบ | อัตราความสำเร็จของกรณีทดสอบไม่น้อยกว่าร้อยละ 90 |
| User Acceptance Testing | ตรวจสอบการยอมรับจากผู้ใช้งานจริง | พนักงานขาย พนักงานคลังสินค้า และผู้จัดการของร้านใช้งานจริงในสถานประกอบการ | แบบสอบถามมาตรวัดลิเคิร์ต 5 ระดับ | คะแนนความพึงพอใจเฉลี่ยไม่น้อยกว่า 4.0 |
