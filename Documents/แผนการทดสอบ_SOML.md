# 2. สิ่งที่อยู่นอกขอบเขตของการทดสอบ

การระบุสิ่งที่ไม่ทดสอบมีความสำคัญเท่ากับการระบุสิ่งที่ทดสอบ เพราะทำให้ผู้อ่านทราบว่าผลการทดสอบยืนยันอะไรไม่ได้

| สิ่งที่ไม่ทดสอบ | เหตุผล |
|-------------------------------------------------------|---------------------------------------------|
| การรับชำระเงินสด การชำระผ่าน Payment Gateway และเครื่องรูดบัตร | อยู่นอกขอบเขตของโครงงานตามข้อ 1.3.6 ระบบไม่มีความสามารถนี้ จึงไม่มีสิ่งให้ทดสอบ |
| การตรวจสอบสถานะการชำระเงินอัตโนมัติผ่าน API ของธนาคาร | ร้านไม่มีสิทธิ์เข้าถึงบริการดังกล่าว การยืนยันรับเงินเป็นการกระทำของพนักงาน |
| การเชื่อมต่อระบบ ERP การแจ้งเตือนผ่าน LINE หรืออีเมล และโมดูลพยากรณ์ความต้องการสินค้า | อยู่นอกขอบเขตตามข้อ 1.3.6 |
| การทดสอบเจาะระบบเชิงลึก (Penetration Testing) | เกินขอบเขตความรู้และเวลาของโครงงาน ทดสอบเฉพาะการควบคุมสิทธิ์ตามที่ NFR-01 กำหนด |
| การทดสอบการกู้คืนระบบจากความเสียหายของฮาร์ดแวร์ | ยังไม่ได้กำหนดนโยบายสำรองข้อมูลกับเจ้าของร้าน จึงยังไม่มีเกณฑ์ให้ทดสอบ |
| การทดสอบบนเบราว์เซอร์รุ่นเก่าและระบบปฏิบัติการอื่นนอกจากที่ NFR-07 ระบุ | ร้านใช้เบราว์เซอร์รุ่นล่าสุดที่กำหนดไว้แล้ว |
| การทดสอบความทนทานระยะยาว เช่น การใช้งานต่อเนื่องหลายวัน | ต้องใช้เวลาเกินกรอบของโครงงาน และต้องทำหลังติดตั้งที่ร้านจริง |

# 3. ระดับการทดสอบ

การแบ่งระดับยึดตามแบบจำลองรูปตัววี (V-Model) ซึ่งกำหนดว่าผลงานของแต่ละขั้นในการออกแบบเป็นฐานของการทดสอบระดับที่คู่กัน ดังนั้นความต้องการในบทที่ 3 จึงเป็นฐานของการทดสอบระดับระบบ ส่วนการออกแบบโมดูลเป็นฐานของการทดสอบระดับหน่วย

| ระดับ | ฐานของการทดสอบ | ตอบคำถามว่า | ตัวอย่างสิ่งที่ทดสอบ | เครื่องมือ | จำนวนที่ทำแล้ว |
|--------------------------|------------|----------|------------------|------------------------|:--------:|
| การทดสอบหน่วย (Unit) | การออกแบบโมดูลในตารางที่ 3.13 และ 3.14 | ตรรกะภายในโมดูลถูกต้องหรือไม่ | การประกอบสตริงรหัส QR · การแปลงใบเสร็จเป็นชุดคำสั่ง ESC/POS · สัญญาว่าการพิมพ์ต้องไม่โยนข้อผิดพลาด | Jest | 34 ข้อ |
| การทดสอบการรวมส่วน (Integration) | สถาปัตยกรรมและโครงสร้างข้อมูลในหัวข้อ 3.5 ถึง 3.7 | โมดูลทำงานร่วมกับฐานข้อมูลจริงได้ถูกต้องหรือไม่ | ธุรกรรมตัดสต็อก · การออกเลขที่ไม่ซ้ำ · การผลักเหตุการณ์ผ่านช่องทางค้าง | Jest ร่วมกับ Supertest | 96 ข้อ |
| การทดสอบระบบ (System) | ความต้องการและเกณฑ์การยอมรับในตารางที่ 3.3, 3.4 และ 3.11 | ผู้ใช้ทำงานจนจบกระบวนการได้หรือไม่ | ขายจนจบแล้วคลังเห็นคิว · จ่ายสินค้าแล้วสต็อกลด · ค้นประวัติย้อนหลัง | Playwright ควบคุมเบราว์เซอร์จริง | 13 ข้อ |
| การทดสอบการยอมรับของผู้ใช้ (UAT) | วัตถุประสงค์ในบทที่ 1 และความคาดหวังของเจ้าของร้าน | ผู้ใช้จริงยอมรับและใช้งานได้จริงหรือไม่ | พิมพ์ใบเสร็จกับเครื่องจริง · แบบประเมินความพึงพอใจ | ดำเนินการกับผู้ใช้จริงของร้าน | ดำเนินการแล้ว ค่าเฉลี่ยความพึงพอใจรวม 4.78 จาก 5 |

นอกจากการทดสอบสี่ระดับข้างต้นซึ่งเป็นการทดสอบแบบพลวัต (Dynamic Testing) คือต้องรันระบบจริง โครงงานนี้ยังใช้การทดสอบแบบสถิต (Static Testing) คือการทบทวนเอกสารโดยไม่รันระบบ รายละเอียดอยู่ในหัวข้อที่ 8

# 6. เกณฑ์เริ่มทดสอบและเกณฑ์จบการทดสอบ

เกณฑ์ทั้งสองชุดเขียนให้ตรวจสอบได้ด้วยข้อเท็จจริง ไม่ใช้ถ้อยคำที่ขึ้นกับความรู้สึก เช่น คำว่าทดสอบจนพอใจ

## 6.1 เกณฑ์เริ่มทดสอบ (Entry Criteria)

| ระดับ | ต้องเป็นจริงก่อนเริ่มทดสอบกรณีแรก |
|------------------------|----------------------------------------------------------------------------|
| หน่วย | โมดูลที่จะทดสอบเขียนเสร็จและเรียกใช้งานได้โดยไม่มีข้อผิดพลาดตอนโหลดไฟล์ |
| การรวมส่วน | ฐานข้อมูลทดสอบถูกสร้างใหม่จากไฟล์โครงสร้างและข้อมูลตั้งต้นสำเร็จ และการทดสอบระดับหน่วยผ่านทั้งหมด |
| ระบบ | ทั้งสี่หน่วยติดตั้งเปิดทำงานพร้อมกันและตอบสนองได้ · การทดสอบสองระดับแรกผ่านทั้งหมด · มีบัญชีผู้ใช้ครบสามบทบาท |
| การยอมรับของผู้ใช้ | ระบบติดตั้งที่ร้านและเชื่อมต่อเครื่องพิมพ์จริงแล้ว · นับสินค้าตั้งต้นเข้าระบบแล้ว · พนักงานได้รับการอบรมการใช้งานแล้ว |

## 6.2 เกณฑ์จบการทดสอบ (Exit Criteria)

| ระดับ | ถือว่าจบเมื่อ |
|------------------------|----------------------------------------------------------------------------|
| หน่วย | กรณีทดสอบระดับหน่วยผ่านครบทุกข้อ และโมดูลที่เกี่ยวข้องกับการตัดสต็อกมีความครอบคลุมของโค้ดไม่ต่ำกว่าร้อยละ 90 |
| การรวมส่วน | กรณีทดสอบระดับการรวมส่วนผ่านครบทุกข้อ และความครอบคลุมของโค้ดโดยรวมไม่ต่ำกว่าร้อยละ 80 |
| ระบบ | เกณฑ์การยอมรับ AC-01 ถึง AC-11 ผ่านครบทุกข้อ และรันซ้ำได้ผลเหมือนเดิมอย่างน้อยสามรอบติดต่อกัน |
| การยอมรับของผู้ใช้ | TC-12 ให้ผลตรงตามที่คาดหวัง และได้รับแบบประเมินความพึงพอใจคืนครบทั้งสามบทบาท |
| ภาพรวมของโครงงาน | กรณีทดสอบ TC-01 ถึง TC-13 มีสถานะชัดเจนทุกข้อ ข้อที่ยังทวนสอบไม่ได้ต้องระบุเหตุผลและแผนดำเนินการไว้ในรูปเล่ม |

ข้อยกเว้นที่ยอมรับได้คือกรณีทดสอบที่ต้องใช้อุปกรณ์หรือสถานที่ซึ่งยังเข้าถึงไม่ได้ในช่วงเวลาของโครงงาน กรณีเช่นนี้ให้รายงานสถานะว่ายังไม่ทวนสอบพร้อมเหตุผล แทนการข้ามไปเฉย ๆ หรือรายงานว่าผ่าน

# 8. การทดสอบแบบสถิตด้วยการทบทวนเอกสาร

การทดสอบแบบสถิตคือการหาข้อบกพร่องโดยไม่รันระบบ ทำได้ตั้งแต่ก่อนมีโค้ด และมีต้นทุนการแก้ไขต่ำกว่าการรอให้พบตอนรัน โครงงานนี้ทบทวนเอกสารโดยไล่เทียบรหัสทุกตัวระหว่างปริญญานิพนธ์ เอกสารข้อกำหนดความต้องการ เอกสาร Use Case และซอร์สโค้ด ผลคือพบข้อบกพร่องที่การรันระบบไม่มีทางพบ ดังนี้

| ข้อบกพร่องที่พบจากการทบทวน | วิธีแก้ไข |
|--------------------------------------------------|--------------------------------------------------|
| ตารางเกณฑ์การยอมรับข้ามหมายเลข AC-05 ไป ทั้งที่กรณีเครื่องพิมพ์ขัดข้องมีทั้งโค้ดและกรณีทดสอบรองรับ | เพิ่ม AC-05 เข้าตารางที่ 3.11 และเชื่อมกับหลักฐาน EV-01 ในตารางสอบกลับ |
| ถ้อยคำของ TC-11 ระบุว่ากรองตามบทบาทผู้กระทำ แต่ AC-11 และระบบจริงกรองตามประเภทการกระทำ | แก้ถ้อยคำในตารางที่ 3.23 ให้ตรงกับเกณฑ์การยอมรับและระบบ |
| บทที่ 4 อ้างเกณฑ์การยอมรับ AC-12, AC-13 และ AC-15 ซึ่งมีเฉพาะในเอกสาร Use Case X ไม่มีในรูปเล่ม | แก้ให้อ้างความต้องการที่มีอยู่จริงในรูปเล่มแทน เพื่อให้บทที่ 1 ถึง 4 ใช้รหัสชุดเดียวกัน |
| แผนภาพสถานะของคำสั่งซื้อไม่มีลูกศรจากสถานะกำลังจัดของไปยังยกเลิก ทั้งที่ตารางสถานะอนุญาต | เพิ่มลูกศรในแผนภาพให้ตรงกับตารางที่ 3.20 |
| เอกสารอ้างอิงแบบจำลองซีโฟร์ถูกอ้างไว้ในบทที่ 3 ซึ่งเป็นบทวิธีดำเนินการ ไม่ใช่บททฤษฎี | ย้ายการอ้างอิงไปไว้ในบทที่ 2 หัวข้อ 2.1.1 และปรับหมายเลขอ้างอิงทั้งบทให้เรียงตามลำดับการอ้างครั้งแรก |
